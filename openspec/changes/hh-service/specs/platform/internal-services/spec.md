# Spec Delta

## Purpose

Границы между ядром и вынесенными сервисами: как сервис получает и записывает вакансии
через внутренний API ядра, как ядро проксирует к сервису публичные эндпоинты, чем
сервисы аутентифицируют друг друга и какими данными владеет каждый.

## ADDED Requirements

### Requirement: Внутренний API доступен только с сервисным токеном
Эндпоинты ядра под `/internal/v1/` MUST требовать `Authorization: Bearer <CORE_INTERNAL_TOKEN>`. Без заголовка, с другим токеном, с JWT пользователя или персональным токеном `tgj_…` ответ SHALL быть 401 `NOT_AUTHENTICATED`, действие не выполняется. Внутренний API SHALL NOT быть доступен под публичным префиксом `/api/v1`.

#### Scenario: Запрос без токена
- **WHEN** запрос к `/internal/v1/vacancies/lookup` пришёл без `Authorization`
- **THEN** ответ 401 `NOT_AUTHENTICATED`

#### Scenario: Токен администратора
- **WHEN** администратор вызывает внутренний эндпоинт со своим access JWT
- **THEN** ответ 401 `NOT_AUTHENTICATED`, вакансии не записаны

#### Scenario: Публичный префикс
- **WHEN** запрос идёт на `/api/v1/internal/v1/vacancies/lookup`
- **THEN** ответ 404

### Requirement: Сервисные токены обязательны в prod
При `APP_ENV=prod` ядро MUST не стартовать без `CORE_INTERNAL_TOKEN` не короче 32 символов, а HH-сервис — без `HH_SERVICE_TOKEN` такой же длины; ошибка называет переменную и не раскрывает значение. В `dev` незаданный токен SHALL получать фиксированное dev-значение, одинаковое у ядра и сервиса.

#### Scenario: prod без токена ядра
- **WHEN** ядро стартует с `APP_ENV=prod` без `CORE_INTERNAL_TOKEN`
- **THEN** старт падает с ошибкой, которая называет `CORE_INTERNAL_TOKEN`

#### Scenario: dev без токенов
- **WHEN** ядро и HH-сервис стартуют в `dev` без токенов
- **THEN** HH-сервис успешно вызывает внутренний API ядра

### Requirement: Сервис читает вакансии по ключам поста
`POST /internal/v1/vacancies/lookup` с `source_post_keys` (1–500 ключей) MUST возвращать сохранённые вакансии с этими ключами в формате модели вакансии ядра, включая архивные и дубли. Ключи, которых нет в базе, SHALL просто отсутствовать в ответе. Пустой список или больше 500 ключей — 422 `VALIDATION`.

#### Scenario: Часть ключей неизвестна
- **WHEN** запрошены ключи `hh-1` и `hh-2`, в базе есть только `hh-1`
- **THEN** ответ 200 с одной вакансией `hh-1`

#### Scenario: Слишком много ключей
- **WHEN** в запросе 501 ключ
- **THEN** ответ 422 `VALIDATION`

### Requirement: Запись пачки вакансий HH через ядро
`POST /internal/v1/sources/hh/vacancies` с пачкой вакансий (1–500) MUST записывать их по правилам сохранения HH (см. `sources/hh-sync`): по `source_post_key`, с пересчётом зарплаты в рубли и возвратом из архива при более новой публикации. Ответ SHALL содержать `inserted` и `updated_existing`. Пачка записывается целиком или не записывается: невалидная вакансия — 422, база не меняется.

#### Scenario: Новая и известная вакансии
- **WHEN** в пачке две вакансии HH, одна из них уже есть в базе
- **THEN** ответ 200, `inserted` 1, `updated_existing` 1

#### Scenario: Невалидная вакансия в пачке
- **WHEN** у одной вакансии пачки нет `raw_text`
- **THEN** ответ 422, ни одна вакансия пачки не записана

#### Scenario: Повтор пачки
- **WHEN** та же пачка отправлена повторно после обрыва соединения
- **THEN** вакансии не задваиваются, `inserted` 0

### Requirement: Ядро проксирует публичные эндпоинты сервиса
Публичный эндпоинт вынесенного сервиса MUST оставаться в ядре с прежним путём и контрактом. Ядро SHALL проверять вход, права и `Idempotency-Key` до обращения к сервису, передавать сервису id пользователя и возвращать клиенту статус и тело ответа сервиса без изменений, включая ошибки в едином формате и поток событий.

#### Scenario: Не администратор
- **WHEN** пользователь без прав администратора вызывает `POST /api/v1/hh/sync`
- **THEN** ответ 403 `FORBIDDEN`, запрос до HH-сервиса не доходит

#### Scenario: Ошибка сервиса
- **WHEN** HH-сервис отвечает 409 `CONFLICT_ACTIVE_RUN`
- **THEN** клиент получает 409 с тем же `detail`

### Requirement: Недоступный сервис — 503 с повтором
Если адрес сервиса не задан, сервис не отвечает за тайм-аут или отвечает не по контракту, ядро MUST отвечать 503 `UPSTREAM_UNAVAILABLE` с `retryable: true`. Остальные эндпоинты ядра и его `/health` SHALL продолжать работать.

#### Scenario: HH-сервис остановлен
- **WHEN** HH-сервис не запущен, администратор открывает `GET /api/v1/hh/status`
- **THEN** ответ 503 `UPSTREAM_UNAVAILABLE`, `retryable: true`
- **AND** `GET /api/v1/health` отвечает `status: ok`

#### Scenario: Адрес не задан
- **WHEN** `HH_SERVICE_URL` пуст
- **THEN** эндпоинты `/api/v1/hh/*` отвечают 503 `UPSTREAM_UNAVAILABLE`

### Requirement: Сервис владеет своей схемой
Данные сервиса MUST храниться в собственной схеме той же базы (HH — `hh`). Сервис SHALL NOT читать и писать таблицы ядра, а ядро — таблицы схемы сервиса; связи между ними — только через API. Ссылки на объекты другой стороны (id пользователя) хранятся без внешних ключей.

#### Scenario: Удаление пользователя
- **WHEN** удаляется администратор, запускавший HH sync
- **THEN** запись HH sync остаётся, в ней прежний id пользователя

### Requirement: Схема сервиса мигрирует при его старте
Сервис MUST при старте применять миграции своей схемы до последней под собственной блокировкой Postgres, независимой от блокировки миграций ядра. Ошибка миграции SHALL останавливать старт сервиса. Данные, перенесённые из схемы ядра в схему сервиса, MUST сохраняться при любом порядке первого старта ядра и сервиса.

#### Scenario: Обновление существующей базы
- **WHEN** база с кэшем выдачи HH и историей sync обновляется до этой версии
- **THEN** строки кэша и история sync доступны HH-сервису без потерь

#### Scenario: Сервис стартовал раньше ядра на пустой базе
- **WHEN** на пустой базе HH-сервис применил свои миграции раньше ядра
- **THEN** после старта ядра в базе одна копия таблиц HH, в схеме `hh`

### Requirement: Здоровье сервиса
У сервиса MUST быть `GET /health` без аутентификации, отвечающий 200 с `status` `ok`, если его база отвечает, иначе `degraded`, и флагом `database`.

#### Scenario: База недоступна
- **WHEN** Postgres не отвечает HH-сервису
- **THEN** `GET /health` сервиса отвечает 200, `status` — `degraded`, `database` — `false`

### Requirement: Трасса проходит через границу сервисов
Вызов между ядром и сервисом MUST передавать контекст трассировки (`traceparent`): спаны сервиса и фоновой задачи, начатой по запросу, SHALL принадлежать трассе исходного запроса.

#### Scenario: Запуск sync
- **WHEN** администратор запускает HH sync, tracing включён
- **THEN** спан запроса ядра, спан HH-сервиса и спан `hh_sync_job` — в одной трассе
