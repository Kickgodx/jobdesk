# JobDesk

**JobDesk** — агрегатор IT-вакансий и рабочее место соискателя (Windows-first). Вакансии собираются из
**Telegram-каналов** (Telethon, ваш аккаунт, MTProto), **HH.ru** (admin-sync) и **ручного импорта**; поля
извлекаются правилами и опционально **AI** (OpenRouter), затем фильтры, дедуп, курсы валют, метрики и экспорт
**Excel/JSON**. Поверх базы — аналитика рынка, матчинг резюме, сопроводительные письма, адаптация резюме,
подготовка к собеседованию (фоновые LLM-джобы) и MCP-сервер для Claude.

> Проект начинался как `tg_jobs_parser` (парсер Telegram-каналов). Имена, хранящие состояние, сохранены:
> база и роль Postgres `tgjobs`, тома Docker `tg_jobs_parser_*` (имя compose-проекта закреплено),
> префикс персональных токенов `tgj_`; MCP-сервер по-прежнему читает и env `TGJOBS_*`.

**Основной способ работы** — веб-интерфейс на **React** + **FastAPI** backend + **PostgreSQL** + **Redis** / `parse-worker` + `llm-worker` + `hh-worker` (Docker Compose). Парсинг ставится в очередь RQ, прогресс пишется в БД (SSE + poll), вакансии сохраняются в PostgreSQL.

Дополнительно — **CLI (Typer)** для первой авторизации Telethon, дампа/импорта БД и отладки без UI.

## Быстрый старт (Docker Compose)

### Требования

- Docker Desktop (Windows / macOS / Linux)
- Файл `.env` рядом с `config.yaml` (см. [Telethon](#telethon-что-подготовить-локально))
- Каталог `sessions/` для файла MTProto-сессии (монтируется в backend)

### Запуск

```powershell
cd путь\к\jobdesk
# Скопируйте .env.example → .env и заполните TELEGRAM_API_ID / TELEGRAM_API_HASH
# В .env должна быть строка COMPOSE_PROFILES=observability (уже есть в .env.example)
docker compose up --build
```

| Сервис   | URL |
|----------|-----|
| **Web UI** | http://localhost:5173 |
| **API** (OpenAPI) | http://localhost:9000/docs |
| **Prometheus** | http://localhost:9090 |
| **Alertmanager** | http://localhost:9093 (сработавшие алерты; также Grafana → Alerting) |
| **Grafana** | http://localhost:3000 (login: `admin` / `GRAFANA_ADMIN_PASSWORD` из `.env`) |
| **Loki** | http://localhost:3100 (API; логи смотрятся в Grafana → Explore) |
| **Alloy** | http://localhost:12345 (UI пайплайна сбора логов и трасс) |
| **Tempo** | http://localhost:13200 → контейнер `:3200` (API; трассы смотрятся в Grafana → Explore → Tempo) |
| **PostgreSQL** | `127.0.0.1:5432` (user/pass/db: `tgjobs` / `tgjobs` / `tgjobs`) |
| **Redis** | `127.0.0.1:16379` → контейнер `:6379` (очереди RQ: parse + LLM) |

В compose backend слушает контейнерный `:8000`, на хост проброшен **`9000`**. Сервис `parse-worker` (тот же образ, команда `jobdesk-parse-worker`) выполняет прогоны парсинга через RQ (очередь `parse`, concurrency=1, volume `sessions/` для Telethon); метрики — контейнерный `:9102` (на хост не публикуется). Сервис `llm-worker` (`jobdesk-llm-worker`) обрабатывает матчинг и письма; метрики — `:9101` (тоже без host mapping, чтобы работал `--scale`). Сервис `hh-worker` (`jobdesk-hh-worker`, очередь `hh`) выполняет HH sync; метрики — `:9103`. Сервис `maintenance-worker` (`jobdesk-maintenance-worker`) — фоновое обслуживание каталога (см. ниже); метрики — `:9104`. Redis хранит очереди на томе `redis_data` с AOF (`appendonly yes`): рестарт контейнера их не теряет.

Полный стек (Prometheus, Grafana, Loki, Alloy, Tempo) включается профилем
`observability` через `COMPOSE_PROFILES=observability` в `.env` (уже есть в
`.env.example`). Без этой переменной `docker compose up` поднимает только
ядро: postgres, redis, backend, workers, frontend, pg-backup
([резервное копирование](#резервное-копирование-pg_dump-по-расписанию)).

Если `.env` создан раньше — добавьте строку `COMPOSE_PROFILES=observability`,
иначе Grafana/Prometheus не стартуют.

Метрики backend — на отдельном порту `API_METRICS_PORT` (контейнерный `:9100`), а не на порту API: на хост он не публикуется, Prometheus ходит на `backend:9100` по Docker-сети. `http://localhost:9000/metrics` отвечает 404.

```powershell
# Только ядро (без observability):
$env:COMPOSE_PROFILES=""; docker compose up --build
```

Либо уберите/закомментируйте `COMPOSE_PROFILES` в `.env`.

### Режимы dev и prod

`APP_ENV` переключает умолчания, сам код один и тот же. Без переменной работает
`dev` — локальная разработка ничего не требует настраивать.

| | `APP_ENV=dev` (по умолчанию) | `APP_ENV=prod` |
|---|---|---|
| Регистрация новых пользователей | открыта | закрыта после первого (админа) |
| Тела запросов/ответов в HTTP-логе | пишутся | не пишутся (резюме и email не уходят в Loki) |
| `JWT_SECRET` | необязателен, эфемерный секрет | обязателен, 32+ символа — иначе backend и воркеры не стартуют |
| refresh-cookie `Secure` | нет (UI по `http://localhost`) | да — нужен HTTPS (`REFRESH_COOKIE_SECURE`) |
| API на не-loopback адресе | backend не стартует (`ALLOW_PUBLIC_DEV=true` — только warning) | разрешено |

`AUTH_REGISTRATION_OPEN` и `HTTP_LOG_BODIES`, заданные явно, действуют в любом
режиме — например, `APP_ENV=prod` + `AUTH_REGISTRATION_OPEN=true`, чтобы
временно пустить нового пользователя.

Порты compose публикуются на `127.0.0.1`: с этой машины всё доступно по
`localhost` как раньше, из сети — нет. К Postgres и Redis с хоста подключайтесь
по `127.0.0.1`, а не `localhost`: порт слушает только IPv4, а `localhost`
сначала пробует `::1` — psycopg на Windows ждёт там весь connect timeout на
каждое новое соединение (браузера это не касается). `BIND_ADDR=0.0.0.0` открывает UI и API
(доступ с телефона, сервер без reverse proxy) — только вместе с `APP_ENV=prod`:
dev-умолчания (открытая регистрация, резюме в логах) безопасны лишь на loopback, и
backend в dev на не-loopback адресе отказывается стартовать. Адрес он узнаёт из
`API_PUBLIC_ADDR` (compose передаёт туда `BIND_ADDR`), без него — из `API_HOST`
(по умолчанию `127.0.0.1`); `uvicorn --host` в обход `API_HOST` проверка не видит.
`INFRA_BIND_ADDR` — то же для Postgres, Redis и observability; у Prometheus, Loki,
Tempo и Alloy аутентификации нет, наружу их открывать не стоит.

Пароли Postgres, Redis и Grafana задаются в `.env` (`POSTGRES_PASSWORD`,
`REDIS_PASSWORD`, `GRAFANA_ADMIN_PASSWORD`), дефолтных нет. Пароли Postgres и
Grafana применяются только при создании пустого тома; сменить на существующем:

```powershell
docker compose exec postgres sh -c 'psql -U tgjobs -c "ALTER ROLE tgjobs PASSWORD ''$POSTGRES_PASSWORD''"'
docker compose exec grafana sh -c 'grafana cli admin reset-admin-password "$GF_SECURITY_ADMIN_PASSWORD"'
```

Минимальный `.env` для сервера:

```env
APP_ENV=prod
JWT_SECRET=...        # python -c "import secrets; print(secrets.token_urlsafe(48))"
# BIND_ADDR=0.0.0.0   # если перед API нет reverse proxy на этой же машине
```

## Web UI (React)

Стек: **Vite + TypeScript + React Router + TanStack Query + Recharts**.

| Страница | Описание |
|----------|----------|
| **Вход** | `/login` — вход и регистрация; без токена остальные страницы недоступны |
| **Парсинг** | Форма парсинга (каналы, даты, специализации, формат работы, AI, пороги score); запуск и очистка кэша LLM — только для админа |
| **Прогон** | Статус «В очереди» → running; прогресс (SSE / poll из БД, переживает F5 и рестарт API), метрики, графики, AI (токены), таблица, экспорт |
| **Импорт** | `/import` — вставка текста вакансии вручную (например, с hh.ru): rules + LLM-разбор (фоновой джобой, с прогрессом) и запись в общую базу; ниже — последние импортированные |
| **HH** | `/hh` — только для админа: sync вакансий с HH.ru (поиск AQA/Python), без LLM; кэш listings + skip detail |
| **Вакансии** | Все уникальные вакансии из PostgreSQL: поиск, фильтры, пресеты, пагинация, сортировка по клику на заголовок; вкладка **Аналитика** |
| **Резюме** | Список резюме пользователя: просмотр текста, создание (вставкой или из PDF/DOCX), редактирование, удаление; «Чего не хватает» по оценкам |
| **Карта рынка** | `/map` — вакансии на плоскости по смыслу, ниши с ростом и зарплатой, место резюме |
| **Спросить базу** | `/ask` — вопрос о рынке словами: цифры по каталогу и короткий ответ LLM только по ним |
| **Обзор** | `/digest` — еженедельный обзор рынка: цифры недели по базе и короткий текст LLM по ним; админ формирует обзор за любую прошедшую неделю |

Возможности таблицы: сортировка asc/desc по дате, зарплате, валюте, формату, грейду, score, match; двухуровневая сортировка «дата + зарплата ₽» (Shift+клик по второй колонке или кнопка над таблицей): по дню поста (UTC), внутри дня — по рублёвой зарплате, или по зарплате, при равной — по дате (`then_by` / `then_order`, в URL, пресетах и экспорте); выбор видимых колонок; модальное окно с полным текстом, оценкой соответствия резюме и ссылками на пост/канал.

## Возможности

### Поиск и пресеты фильтров

Поиск по тексту — полнотекстовый (Postgres FTS): хранимая generated-колонка
`vacancies.search_tsv = to_tsvector('russian', cleaned_text)` с GIN-индексом
`ix_vacancies_search_tsv`, запрос через `websearch_to_tsquery`. Со стеммингом:
«разработчик» находит «разработчиков».

С `q` релевантность (`ts_rank`) упорядочивает первые 1000 совпадений в выбранной
сортировке (`FTS_RANK_WINDOW` в `backend/db/vacancy_repository.py`; по умолчанию —
1000 самых свежих). Остальные совпадения идут за ними в выбранной сортировке,
`total` считает все. Тот же порядок — в экспорте. Без окна `ts_rank` по всем
совпадениям частого слова на 45 тыс. вакансий стоил ~1.4 с на запрос, с окном —
десятки миллисекунд.

Список вакансий по умолчанию опирается на частичный индекс
`ix_vacancies_active_post_date (post_date DESC NULLS LAST, id) WHERE NOT is_duplicate AND archived_at IS NULL`
(ORDER BY + COUNT без seq scan). `GET /vacancies` отдаёт slim-карточки с
`preview`; полный текст — `GET /vacancies/{id}`. COUNT кэшируется ~1 с в
процессе API.

Специализация — это роль (QA, Automation QA, Backend, Frontend, AI, DevOps…),
а языки, фреймворки, БД и инструменты (Python, Go, Java, PHP, C++, .NET, 1С,
PostgreSQL, Kafka…) — **технологии** вакансии (`technologies`). AQA на Python —
`["Automation QA"]` + технология `Python`, ML на Python — `["AI"]` + `Python`.
Языки, которые LLM или пользовательский словарь всё же ставят специализацией,
переносятся в технологии детерминированно (`split_specializations` в
`jobdesk/config/schema.py`); «Python Developer» без другой роли получает роль
`Software Engineer`. Имена технологий канонические: `Golang` → `Go`,
`Apache Kafka` → `Kafka`, регистр — по словарю; все варианты 1С (`1С:Предприятие 8.3`,
`1C:ERP`, `1С КА`) — одна технология `1С` (миграция 038 привела и сохранённые вакансии).
Технологии из открытых источников — «ключевые навыки» HH и ответ LLM — при записи чистятся
(`clean_technology_names`): практики и навыки по-русски («Функциональное тестирование»,
«Английский язык», «Коммуникабельность») убираются, аббревиатуры (ООП, СКД) остаются; списки в одной
строке делятся («Python 3.13+, FastAPI» → Python, FastAPI; «C# или C++»), у известной технологии
отрезается версия (Vue 3 → Vue; «ISO 27001» остаётся), из фразы-требования («Опыт работы с
мониторингом (Grafana, Kibana)») берутся перечисленное в скобках и технологии словаря.

Фильтр «Технологии» (`?technology=Python&technology=Go`) — любая из выбранных;
вместе со специализациями — через **И**: «Automation QA» + «Python» — только AQA
на Python. Чипы — 30 самых частых технологий под остальными фильтрами
(`GET /vacancies/technologies`), прочие — через поле поиска. Старые ссылки и
пресеты с языком в `specialization` превращаются в фильтр по технологии. Тот же
фильтр есть у прогона (`filters.technologies`).

Набор фильтров сохраняется как именованный пресет (`saved_filters`, JSON с
полями `VacancyQuery`) и применяется одной кнопкой. Пресеты приватные —
привязаны к пользователю.

### Аналитика

Вкладка **Аналитика** на странице вакансий: агрегация в SQL, без выгрузки
строк, с теми же фильтрами, что и список. По умолчанию запросы аналитики
идут с `include_archived=true` (активные **и** архивные), чтобы история по HH
не обрезалась TTL; поэтому вакансий в графиках бывает больше, чем в выборке
списка. Флажок «Учитывать архивные вакансии» на вкладке это отключает — тогда
аналитика считается по той же выборке, что и список.

- `GET /analytics/salaries` — медиана/квартили/распределение
  `detected_salary_avg_rub` по грейдам, специализациям и формату работы;
  помесячная и **погодовая** динамика; разрезы год×грейд / год×формат и
  месяц×грейд / месяц×формат (для drill-down).
  Квантили групп: min, p10, p25, медиана, p75, p90, max.
- UI: режим «Все годы (YoY)» или выбор года → месяц к месяцу. Рядом с
  гистограммой распределения — «Разброс зарплат по грейдам» (box-plot: ящик
  p25–p75, медиана, усы p10–p90; min/max — в подсказке, чтобы выбросы не
  растягивали ось).
- `GET /analytics/sources` — качество канала: число вакансий, доля с
  зарплатой, средний `vacancy_score`, дубли и доля уникальных постов.
  В `vacancies` попадает только первый пост с данным текстом, а каждое появление
  поста Telegram записывается в `vacancy_sightings`: оригинал или дубль со
  ссылкой на вакансию. Дублем считается похожий текст в другом канале, перепост
  в том же канале и текст, уже бывший в БД с прошлых прогонов. Доля уникальных —
  посты канала с новым текстом от всех его постов; канал-агрегатор, который только
  перепечатывает чужое, виден с нулём вакансий и низкой долей. Канал и даты фильтра
  берутся у самого поста, остальные фильтры — у вакансии. У HH дубли — это
  мультигородные копии.
- `GET /analytics/companies` — топ компаний.
- `GET /analytics/technologies` — технологии (без собственного фильтра по технологии):
  **премия** — медиана рублёвой зарплаты с технологией против медианы без неё внутри
  одного грейда, средневзвешенно по грейдам, где в обеих группах от 5 вакансий
  (25 самых частых технологий среди вакансий с зарплатой; меньше 10 сравнимых вакансий —
  `null`). Так Kubernetes не получает «премию» только за то, что чаще встречается у
  senior. **Спрос по месяцам** — доля вакансий с технологией (8 самых частых, до 24
  месяцев). **Растут и падают** — доля за последние 30 дней против предыдущих 30
  (от последней даты поста; в каждом окне нужно от 30 вакансий). Доля зависит и от
  набора каналов: новый фронтенд-канал поднимет React.
- `GET /vacancies/metrics` — в том числе топ-50 технологий (`technology_top`,
  график «Топ технологий»).

**Какие технологии просят вместе.** Раздел вкладки «Аналитика» (`GET /analytics/technology-graph`,
те же фильтры, без собственного фильтра по технологии): граф самых частых технологий (`nodes`,
по умолчанию 40, до 80). Линия — пару просят в одной вакансии заметно чаще, чем случайно:
сила связи — lift, `n_ab · N / (n_a · n_b)`; сама по себе частота пары не годится — Python и
SQL встречаются вместе просто потому, что обе частые. Пары реже 3 вакансий отбрасываются, у
каждой технологии рисуются до 3–5 самых сильных связей (выбирается, по умолчанию 5) не слабее
выбранного порога (×1,5 по умолчанию). Размер узла — число вакансий, цвет — роль, с которой технология встречается чаще
всего. Клик по технологии — список того, с чем её просят (доля её вакансий и lift). Пары
считаются одним SQL по технологиям каждой вакансии (LATERAL), на 2,5 тыс. вакансий — 0,3 с;
расклад графа — во фронтенде, без библиотек.

**Жизнь вакансии.** Раздел вкладки «Аналитика» (`GET /analytics/lifetime`, те же фильтры): сколько
вакансия остаётся на рынке по её публикациям в Telegram — от первой до последней публикации текста,
включая перепосты и перепосты с правками. Это видимость, а не дата закрытия. Повторно публикуемые —
вышедшие в 2+ разных дня (UTC); долгие — со сроком от 21 дня (порог флага «висит давно»). Показаны
доля повторных, медиана и p90 их срока, корзины срока, разрезы по ролям и грейдам (от 10 вакансий),
компании с повторными публикациями и 15 самых долгих вакансий (клик открывает карточку). HH не
входит: синк читает окно по дате публикации, и пропажа из выдачи не значит, что вакансию закрыли.

**Рыночная вилка вакансии.** В карточке вакансии — блок «Рынок для похожих»
(`GET /vacancies/{id}/market-salary`): квантили рублёвой зарплаты похожих вакансий за год
до вакансии (с архивом, без дублей). Похожие подбираются по лестнице: тот же грейд + роль +
хотя бы одна технология → грейд + роль → грейд + технология → только роль; берётся первая
ступень, где похожих не меньше 8, и она подписана в карточке. Если у вакансии есть
зарплата — точка на полосе и доля похожих, у которых зарплата не выше.

**Ориентировочная зарплата.** В карточке вакансии без зарплаты — блок «Ориентировочная зарплата»
(`GET /vacancies/{id}/salary-estimate`, без LLM): медиана и p25–p75 рублёвых зарплат 15 ближайших
по эмбеддингу вакансий с зарплатой того же грейда (грейд неизвестен — любого) за год до поста, с
архивом, без дублей; меньше 8 таких — оценки нет. Рядом — 5 ближайших из них (клик открывает
карточку). Эмбеддинг хорошо ловит роль и стек, но плохо — уровень, поэтому грейд — жёсткий фильтр.
Оценки хранятся в `vacancy_salary_estimates` (миграция 050): лидер API пересчитывает их после
каждого прохода индексации эмбеддингов — новые, изменённые и старше 7 дней, до 1000 за проход; без
свежей оценки карточка считает её на лету. Оценка не попадает ни в `detected_salary_avg_rub`, ни в
аналитику, ни в строки списка. В фильтрах списка под «Только с указанной зарплатой» — флажок
«…и с оценкой по похожим» (`salary_estimates=true`): вакансии с оценкой тоже проходят фильтр
`has_salary`; метрики и `/analytics/*` флаг игнорируют. Точность — `python -m jobdesk.cli db
salary-estimate-eval` (только чтение): каждая вакансия с зарплатой оценивается так, будто зарплаты
нет. На живой базе (718 вакансий с зарплатой) медианная ошибка 25,5%, реальная зарплата внутри
p25–p75 у 48,6%; у лестницы «Рынка для похожих» — 28,2% и меньше вакансий с оценкой (617 против 679).

**Профиль компании и флаги.** Название компании в карточке вакансии и в «Топе компаний» —
ссылка на страницу `/company` (`GET /companies/profile?name=`): все вакансии компании в
базе (с архивом), активные, даты, зарплата p25–p75 и медиана, роли, технологии, грейды,
каналы и 20 последних вакансий. Написания одной компании («Bell Integrator» и
«BELL INTEGRATOR», «ООО Ромашка» и «Ромашка») сводятся по `vacancies.company_key` — так же
считается и топ работодателей. В карточке вакансии — флаги по правилам
(`GET /vacancies/{id}/flags`, без LLM): текст публиковали в 3+ разных дня; между первой и
последней публикацией 21+ день; у компании 5+ вакансий той же роли за 90 дней (массовый
найм или аутстафф); зарплата не указана.

**История публикаций.** В карточке вакансии — блок «История публикаций»
(`GET /vacancies/{id}/history`), если вакансию публиковали больше одного раза: первая
публикация, перепосты того же текста и перепосты с правками (см. дедуп между прогонами) с
датой, каналом и ссылкой на пост. У перепоста с правками — что поменялось по сравнению с первой
публикацией: зарплата (в валюте поста, а не в рублях: иначе разница курсов выглядела бы
правкой), формат работы, город, добавленные и убранные технологии (страну LLM пишет по-разному —
«Russia», «РФ», — она не сравнивается). Пропавшее
значение изменением не считается (агрегатор часто перепечатывает пост без зарплаты), а
технология — только если её название действительно появилось в тексте или ушло из него.
Изменения пишутся в появление поста (`vacancy_sightings.changes`) при прогоне и при разовом
склеивании `db merge-duplicates` (цепочки проходов выпрямляются: скрытая копия ссылается на
корневую исходную, изменения — от первой публикации). Строка вакансии остаётся первой публикацией. У скрытой
копии вместо истории — ссылка на исходную вакансию.

Зарплаты приводятся к рублям по курсам ЦБ (`exchange_rates`), метка
`salary_display` показывает дату курса (`null`, если курсов в базе нет). Зарплата без валюты считается в
`fx.default_currency_if_missing` (`RUB`). Фильтр `has_salary` смотрит на ту же
рублёвую сумму, что и аналитика: `true` — только вакансии с ней, `false` — без неё.
Пересчёт (`POST /fx/refresh`, `POST /fx/recalculate-rub`) обновляет и архивные вакансии.

Агрегаты (`/vacancies/metrics`, `/analytics/*`) кэшируются в памяти API на `ANALYTICS_CACHE_SECONDS` (30 с) по набору фильтров; запись вакансий в том же процессе сбрасывает кэш сразу, запись из воркера видна не позже чем через TTL. Фильтры по специализации и технологии на Postgres идут по GIN-индексам (`detected_specializations` — `JSONB`, миграция 019; `technologies` — `JSONB`, миграция 037). `config.yaml` перечитывается только при изменении файла (кэш по mtime).

### Новые каналы из пересылок

Каналы-агрегаторы пересылают вакансии из других каналов, и такие пересылки подсказывают,
какие источники стоит добавить. Прогон запоминает каждый пост, пересланный из канала (не от
пользователя и не со скрытым отправителем): откуда он, в какой наш канал и прошёл ли он как
вакансия. Username и название исходного канала берутся из того же ответа истории, без
лишних запросов к Telegram. Хранится это в `telegram_forwards` (канал + id поста:
перечитанное окно не удваивает счётчики) и `channel_candidates`.

На странице **Парсинг** под полем каналов — свёрнутый блок «Кандидаты из пересылок»
(`GET /channels/candidates`, только admin). В нём каналы с публичным username, которых нет
ни в `config.yaml`, ни среди уже читавшихся (по чекпоинтам). Порядок — по числу
пересланных вакансий, затем по числу пересылок. Видно, в какие наши каналы пересылают, и
есть ссылка на последний пересланный пост в источнике. «Добавить» вписывает канал в форму
прогона, «Скрыть» убирает кандидата из списка (`PATCH /channels/candidates/{id}`, вернуть
можно в «Показать скрытые»).

### Обзор рынка за неделю

Страница **Обзор** (`/digest`): раз в неделю — что изменилось на рынке по базе вакансий.
Неделя — понедельник–воскресенье по UTC, вакансия относится к неделе по дате поста;
считаются уникальные вакансии с архивом (Telegram и HH). Цифры считает backend: число
вакансий против прошлой недели и среднего за 4 недели, доля с зарплатой, роли, формат
работы, источники и компании с изменением к прошлой неделе, «новые компании» (первая
вакансия в базе — на этой неделе), медианы рублёвой зарплаты по грейдам за 28 дней до
конца недели против 28 дней перед ними (от 10 вакансий в группе) и технологии, чья доля
сильнее всего выросла или упала против 4 недель до недели (если в неделе от 20 вакансий,
а в базе сравнения от 40; изменение от 1 п.п.).

По этим цифрам LLM пишет короткий текст (модель писем, промпт
`MARKET_DIGEST_PROMPT_VERSION`): только числа из фактов, без причин и прогнозов. Новые
компании — только из списка новых (а не любая, у которой не было вакансий на прошлой
неделе); зарплаты сравниваются по грейдам, общая медиана — только если грейды идут в ту же
сторону, иначе изменился состав грейдов. Один
вызов в неделю, своим клиентом — вне суточного бюджета пользовательского LLM. Модель
недоступна или нет ключа — обзор сохраняется только с цифрами и пометкой.

Обзор за прошедшую неделю формирует фоновое обслуживание (проверка раз в час; где именно — `MAINTENANCE_BACKEND`, см. `config.md`), если в неделе были
вакансии (`digest.enabled`, текст — `digest.llm_summary`, см. `config.md`). Прошлые недели
сами не досчитываются: админ формирует обзор за любую завершённую неделю кнопкой на
странице (`POST /digests`, повторно — с пересчётом). Читать обзоры может любой
залогиненный.

### Карта рынка

Страница **Карта рынка** (`/map`): каждая точка — вакансия, рядом стоят похожие по смыслу текста. Самые
свежие 8000 уникальных вакансий за год (`ai.embeddings.map_max_points`) с эмбеддингом текущей модели
сжимаются PCA до 50 измерений и t-SNE (косинус) до плоскости; k-means делит её на ниши (около 130
вакансий на нишу, от 4 до 20). Подпись ниши — без LLM: самая частая роль и технологии, которых в нише
заметно больше, чем по рынку («AI · Python, LLM», «Software Engineer · 1С»). У ниши — медиана зарплаты и
рост: доля за последние 30 дней против предыдущих 30 (зависит и от набора каналов).

На карте: подписи ниш, подсказка по наведению, клик открывает вакансию, колесо — масштаб, перетаскивание
— сдвиг; клик по строке таблицы ниш подсвечивает нишу. Выбранное резюме ставится в среднюю точку 15
ближайших к нему вакансий, они подсвечены (`GET /market-map?resume_id=`). Карту пересчитывает фоновое обслуживание
раз в `ai.embeddings.map_interval_hours` (24 ч) или по кнопке админа: `POST /market-map/rebuild` отвечает 202
сразу (мало вакансий с эмбеддингами — 422), а пересчёт идёт в фоне — пока он не закончен, `GET /market-map`
отдаёт `rebuild_pending: true`, и страница опрашивает его раз в 5 секунд. На 2,4 тыс. вакансий расчёт идёт
около 5 секунд, на 8 тыс. — около минуты. Хранится только последняя карта (`market_maps`, `market_map_points`,
миграция 048). Нужен `scikit-learn`.

### Спросить базу

Страница **Спросить базу** (`/ask`): вопрос о рынке словами — «сколько платят senior Python-бэкендерам
на удалёнке?», «Go или Python: где больше вакансий?», «а для middle?». Модель не отвечает сама и не
пишет SQL: первым вызовом она переводит вопрос (и до 3 прошлых вопросов с их фильтрами) в план по белому
списку — роли, технологии, грейд, формат, даты, «только с зарплатой», слова поиска, нужные разделы цифр
(число вакансий, зарплаты по грейдам и форматам, компании, технологии с премией и динамикой, вакансии по
месяцам, жизнь вакансии, каналы, примеры) и до 4 вариантов сравнения. Backend приводит план к фильтрам
каталога (роль — по словарю и синонимам: «Backend developer» → Backend; грейд, названный в вопросе, не
теряется), считает цифры теми же функциями, что вкладка «Аналитика» (с архивом), и вторым вызовом модель
пишет короткий ответ только по ним. Вопрос не о рынке получает отказ без второго вызова.

Под ответом — фильтры, по которым считали (со ссылкой «Открыть в списке»), нераспознанные слова и
примеры вакансий (открывают карточку). Задача — LLM-джоба `kind=ask_market` (`POST /market-chat/ask`,
итог в `ask_market_result` у `/llm-jobs/{id}`, SSE и отмена — как у остальных); в суточной квоте вопрос —
один вызов. Модель — модель писем; версия промпта — `ASK_MARKET_PROMPT_VERSION`. Диалог хранится
только во вкладке браузера (sessionStorage).

### Матчинг резюме к вакансиям

Резюме хранятся текстом и управляются на вкладке **Резюме** (создание,
просмотр, редактирование, удаление); на странице «Вакансии» резюме только
выбирается в панели над таблицей. Дальше оценка идёт
**по одной вакансии**: открываете карточку → кнопка «Оценить резюме» рядом с
«Открыть пост» / «Канал» → фоновая LLM-джоба (см. ниже). В карточке появляются
overall score, разбивка по измерениям (роль, навыки, грейд, домен, формат),
confidence оценки, пояснение и списки совпадающих / недостающих навыков
с приоритетом (critical/important/secondary) и evidence, а также сильные
стороны и риски кандидата.

- LLM отвечает только за оценку измерений и объяснение: итоговый
  `overall_score` считает backend детерминированно — взвешенная сумма
  breakdown (роль 30%, навыки 35%, грейд 20%, домен 10%, формат 5%) плюс
  penalty за пробелы по critical-требованиям (1 → cap 69, 2+ → cap 59).
- Оценка сохраняется парой `(resume_id, vacancy_id)`: повторное открытие
  карточки отдаёт её из БД, токены не тратятся. Кнопка «Переоценить резюме»
  (`force=true`) запускает LLM заново.
- Вместе с оценкой хранятся запрошенная модель матчинга (настроенная, а не
  ответившая fallback-модель — та остаётся в `model`) и версия промпта
  (`MATCH_PROMPT_VERSION`). Если с тех пор сменили `ai.match_model` (пусто →
  `ai.model`) или версию промпта, оценка **устарела**: ответы `GET`/`POST`, итог
  LLM-задачи и элемент списка вакансий отдают `stale: true` / `match_stale: true`,
  а `POST` без `force` пересчитывает её (202) вместо ответа из БД. В карточке у
  такой оценки — пометка «переоцените»; колонка Match и сортировка по ней не
  меняются. Оценки до миграции 030 по версии не устаревают (запрошенной
  считается фактическая модель).
- Посчитанные скоры видны в колонке **Match**, по ним же работает сортировка
  (`sort_by=match_score` при выбранном резюме; без `resume_id` — 422).
- Мэтчинг и письма — фоновые джобы (`llm_jobs`): кэш → 200; иначе 202 +
  `job_id`. В Docker: Redis Queue (RQ) + сервис `llm-worker` (тот же образ,
  `jobdesk-llm-worker`). UI ждёт через SSE `GET /llm-jobs/{id}/events`
  (fallback — poll). Параллелизм: `--scale llm-worker=N` и
  `ai.interactive_per_user_limit`; `ai.interactive_concurrency` — для
  inprocess / ориентир scale. Воркер — RQ ``SimpleWorker`` (без fork: меньше
  пик RAM, метрики в том же процессе). Метрики — контейнерный порт 9101
  (Prometheus `dns_sd` по имени `llm-worker`, все реплики; на хост не
  пробрасывается). Локально без Redis: `LLM_JOB_BACKEND=inprocess`.
- **Лимиты расхода.** `ai.requests_per_minute` при заданном `REDIS_URL` — общий
  на все процессы (API, parse-worker, все реплики llm-worker): счётчик минутного
  окна в Redis, а не лимитер в памяти каждого процесса. Без Redis или при его
  сбое — локальный лимит процесса. Не-админу доступно `LLM_USER_DAILY_CALLS`
  вызовов LLM в сутки (UTC; по умолчанию 100, `0` — без квоты): каждая
  поставленная мэтч/письмо-джоба и каждый текст ручного импорта, ушедший в LLM.
  Сверх квоты — 429 `LLM_QUOTA_EXCEEDED`; импорт дочитывает остаток правилами.
  Ответы из кэша квоту не тратят; админ (владелец ключа) без квоты. Вызов за
  мэтч или письмо возвращается в квоту (в сутки списания), если задача кончилась
  `error` или отменена до ответа модели; удаление резюме возвращает вызовы его
  задач в очереди.
  Общий потолок пользовательского LLM — `ai.interactive_daily_request_budget`:
  запросов мэтчинга и писем всех пользователей в UTC-сутки (счётчик в Redis; без
  Redis — на процесс). Исчерпан — новые мэтчи и письма сразу получают 429
  `LLM_QUOTA_EXCEEDED` (без задачи и без траты квоты) до полуночи UTC, после
  сброса снова работают без рестарта. Парсинг доступен только админу и бюджетом
  не ограничен.
- Модель матчинга задаётся отдельно от модели парсинга: `ai.match_model`
  (+ `ai.match_reasoning_enabled` для reasoning-моделей) — качество здесь
  важнее скорости, вызовов на порядок меньше. Глубина рассуждений —
  `ai.match_reasoning_effort` (`high`, `xhigh`, …), одна на все модели:
  OpenRouter сам сводит уровень к ближайшему, который поддерживает модель.

### Чего не хватает (сводка пробелов резюме)

На странице **Резюме** у выбранного резюме — блок «Чего не хватает»: недостающие навыки
из всех его сохранённых оценок (`GET /resumes/{id}/skill-gaps`, без вызова LLM). Навыки
LLM пишет свободным текстом («MySQL / ClickHouse», «Go (5+ лет)»), поэтому технологии в них
ищутся по словарю — технологии `config.yaml`, их алиасы и технологии, которые есть хотя бы
у 5 активных вакансий каталога (роли вроде «Backend» не считаются) — и сводятся к
каноническим именам. Остальное группируется по тексту без пояснений в скобках. Для
каждого пробела: в скольких вакансиях не хватает, с каким приоритетом (у вакансии
считается наивысший), доля от оценённых, до трёх примеров (открываются в карточке) и у
технологий — спрос: сколько активных вакансий базы её требуют. Порядок — по весу
`3·critical + 2·important + secondary`.

### Резюме и рынок

На странице **Резюме** у выбранного резюме — блок «Резюме и рынок» (`GET /resumes/{id}/market`,
без вызова LLM): что рынок платит и требует там, где резюме ближе всего. Ближайшие — 50
уникальных вакансий за год (с архивом), ближайших к тексту резюме по эмбеддингу (тот же
вектор, что у «Подбора под резюме»). По ним — доли ролей и грейдов (кем рынок видит
резюме), квантили рублёвой зарплаты по 30 ближайшим вакансиям с зарплатой (от 8, иначе
вилки нет) и технологии, которые есть хотя бы у 10% ближайших, с отметкой «есть в резюме».
Технология засчитывается резюме, если её нашёл словарь «Чего не хватает» (с алиасами:
Golang → Go) или её название целым словом есть в тексте («Atlassian Jira» → Jira); «покрытие» — средняя по
ближайшим доля технологий вакансии, названных в резюме. Нужны эмбеддинги
(`ai.embeddings.enabled`); выключены или провайдер недоступен — 503 `UPSTREAM_UNAVAILABLE`.
Если версий резюме несколько, блок позволяет сравнить, какую рынок видит выше.

### Что если выучить

На странице **Резюме** у выбранного резюме — блок «Что если выучить» (`GET /resumes/{id}/what-if`,
без вызова LLM): какая недостающая технология сильнее всего расширит выбор вакансий. Сегмент — 200
уникальных вакансий за год, ближайших к резюме по эмбеддингу; вакансия «подходит», если резюме
называет не меньше 70% её технологий (как «есть в резюме» у «Резюме и рынок»). Для технологий, которых
нет в резюме и которые нужны хотя бы в 5 вакансиях сегмента (и 3% его): в скольких вакансиях нужна,
сколько станут подходящими, если добавить только её, рост среднего покрытия, зарплатная премия (как
во вкладке «Аналитика»: в самом частом грейде сегмента, иначе по грейдам самой частой роли) и медиана
зарплаты вакансий с ней. Многословные русские практики («Написание автотестов») — не технологии и в
список не входят. Отметки в таблице считают эффект нескольких технологий вместе прямо в браузере.
Нужны эмбеддинги, иначе 503 `UPSTREAM_UNAVAILABLE`.

### Куда расти (карьерная траектория)

На странице **Резюме** под «Что если выучить» — блок «Куда расти» (`GET /resumes/{id}/career-paths`,
без вызова LLM): следующий грейд своей роли и соседние роли, что выучить по дороге и сколько там платят.
Позиция резюме — самые частые роль и грейд среди 50 ближайших к нему по эмбеддингу вакансий за год
(как профиль «Резюме и рынок»); соседние роли — те, что встречаются среди 300 ближайших хотя бы
5 раз и в 3% из них (до 6 ролей). Каждая цель считается по 300 вакансиям роли, ближайшим к резюме, —
иначе широкая роль вроде «Software Engineer» смешала бы в один маршрут 1С, Go и C++. Из них берётся
грейд цели (у соседней роли — грейд резюме, у шага вверх — ближайший старший грейд), если в нём не
меньше 20 вакансий с технологиями, иначе все грейды. По цели: доля вакансий, которым резюме подходит
уже сейчас (≥ 70% технологий, правило «Что если выучить»), маршрут до 5 технологий — каждая следующая
открывает больше всего вакансий вместе с уже выбранными (шаги в конце, которые ничего не открывают,
отбрасываются), медиана зарплаты (от 8 вакансий) и её отличие от медианы текущей позиции. Нужны
эмбеддинги, иначе 503 `UPSTREAM_UNAVAILABLE`.

### Карьерный отчёт

На странице «Резюме» у выбранного резюме — кнопка «Карьерный отчёт (PDF)»: страница
`/resumes/{id}/report`, свёрстанная под печать. Кнопка «Сохранить в PDF / печать» открывает
печать браузера, где PDF сохраняется штатно (A4, без меню и шапки приложения, заголовки
таблиц повторяются на новой странице). В отчёте:

- **Главное** — медиана зарплаты похожих вакансий, доля их технологий, названных в резюме,
  сколько похожих подходят по стеку; кем рынок видит резюме, что добавить в стек первым и
  что даст следующий грейд;
- **Резюме и рынок**, **Что выучить**, **Куда расти** — те же расчёты, что панели страницы
  «Резюме» (`/resumes/{id}/market`, `/what-if`, `/career-paths`), компактно;
- **Чего не хватает по оценкам** — если у резюме есть сохранённые оценки соответствия;
- **Подходящие вакансии** — 10 с лучшей сохранённой оценкой, а без оценок — 10 ближайших по
  смыслу, со ссылками на посты.

Отчёт собирается из готовых эндпоинтов и LLM не вызывает; разделы, которым нужны эмбеддинги,
без них показывают пояснение, остальные строятся.

### Сопроводительные письма

Из карточки вакансии — кнопка «Сопроводительное» рядом с «Оценить резюме»:
LLM пишет черновик отклика под конкретную вакансию по выбранному резюме
(120–200 слов, язык — по языку вакансии, без выдуманного опыта). Тон —
выбором рядом с кнопкой (нейтральный / дружелюбный / формальный). Если пара
уже оценена, в промпт подмешивается сохранённый матч (сильные стороны).

- Письмо хранится парой `(resume_id, vacancy_id)` в `cover_letters`:
  повторное открытие карточки отдаёт его из БД, токены не тратятся.
  «Перегенерировать письмо» (`force=true`) вызывает LLM заново;
  `DELETE` сбрасывает сохранённый вариант.
- `POST` без `force` отдаёт сохранённое письмо, только если совпадает тон и
  письмо не устарело; иначе генерирует заново (202) в запрошенном тоне.
  Устаревание — как у оценки: сменилась модель писем (`ai.cover_letter_model` →
  `match_model` → `model`) или `COVER_LETTER_PROMPT_VERSION`; тогда `stale: true`
  и пометка «перегенерируйте» в карточке. Тон на `stale` не влияет.
- Текст открывается в редактируемом поле — правки локальные, для кнопки
  «Копировать»; в БД остаётся исходный вариант LLM.
- Модель — `ai.cover_letter_model` (пусто → `match_model` → `model`),
  reasoning-флаг и уровень общие с матчингом (`ai.match_reasoning_enabled`,
  `ai.match_reasoning_effort`).

### Смысловой поиск, похожие вакансии и подбор под резюме

У каждой уникальной вакансии — эмбеддинг (OpenRouter `/embeddings`, `ai.embeddings.model`,
по умолчанию `qwen/qwen3-embedding-8b` в 1536 измерениях) в таблице `vacancy_embeddings`
(pgvector, HNSW по косинусу). Текст для вектора — роль, грейд, технологии, формат и сам пост;
текст запроса и резюме уходит с инструкцией модели (`query_instruction` / `resume_instruction`,
формат Qwen3) — на коротких запросах без неё Qwen3 заметно хуже. Модель выбрана eval'ом на
своих вакансиях (см. «Eval моделей эмбеддингов»): против `text-embedding-3-small` — nDCG@10
поиска 0.84 против 0.68, «Похожих» 0.87 против 0.71. Смена модели безопасна: пока каталог
переиндексируется, поиск, подбор и «Похожие» видят только векторы текущей модели, а карту
рынка пересчитывается, когда переиндексация закончена.
Индексирует фоновое обслуживание раз в `ai.embeddings.sweep_interval_seconds` (5 мин): новые,
изменённые (по `updated_at` и хэшу текста) и посчитанные другой моделью; вакансия,
которую просто встретили снова, к API не идёт. Пачку, которую провайдер отверг, проход
повторяет по одной вакансии: вакансия, падающая сама по себе, откладывается на сутки (или до
изменения текста), остальные индексируются; три неудачи подряд — провайдер недоступен,
проход останавливается до следующего интервала. Отдельный клиент OpenRouter — без суточного
бюджета пользовательского LLM: каталог из 2,3 тыс. вакансий индексируется примерно за
минуту и несколько центов.

- **Похожие вакансии** — блок в карточке (`GET /vacancies/{id}/similar`): ближайшие
  активные, без почти того же текста (перепост с правками, ближе
  `ai.embeddings.near_duplicate_distance`) и не больше двух от одной
  компании. Клик открывает вакансию поверх текущей.
- **Смысловой поиск** — переключатель «По словам / По смыслу» у поиска
  (`search_mode=semantic`): совпадения — 300 ближайших к запросу вакансий под остальными
  фильтрами, при сортировке по умолчанию — ближайшие первыми. Это условие фильтра, поэтому
  аналитика и экспорт считают ту же выборку. Вектор запроса кэшируется в памяти процесса;
  провайдер недоступен — 503 `UPSTREAM_UNAVAILABLE`, без тихого отката к словам.
- **Подбор под резюме** — при выбранном резюме флажок «Подбор под резюме»
  (`sort_by=resume_fit`): список по близости эмбеддингов вакансии и резюме (вектор резюме
  хранится в `resume_embeddings` и пересчитывается при смене текста), вакансии без вектора
  — в конце. Кнопка «Оценить топ-N» ставит одну LLM-задачу `match_batch`
  (`POST /resumes/{id}/match-batch`, до 20 вакансий): свежие оценки не пересчитываются,
  квота — за каждую оценённую, прогресс — по SSE, итог — в колонке Match.

`GET /vacancies/semantic-status` — сколько вакансий уже проиндексировано текущей моделью.
Нужен Postgres с расширением vector: compose собирает его из `docker/postgres`
(`postgres:16-alpine` + pgvector, тот же musl и сортировка строк, что у прежнего образа —
том `pgdata` подходит без REINDEX).

**Связаться с рекрутером.** В карточке вакансии — блок «Связаться с рекрутером»
(`GET /vacancies/{id}/contacts`, без LLM): Telegram-аккаунты и email из текста. Каналы и их подписи
отсеиваются: каналы-источники, кандидаты из пересылок и `sources.channels`; упоминания, у которых
ближе реклама канала («Подписаться на наши каналы», «Вакансия опубликована в»), чем слова отклика;
упоминание без слов отклика, стоящее под 30%+ вакансий своего канала (от 5). Контакты со словами
отклика рядом («Контакты:», «резюме», «Отклики») — первыми, остальные — серой кнопкой. Кнопка
открывает чат по ссылке `t.me/<username>?text=…` или `mailto:` с подставленным текстом:
сопроводительным письмом с вашими правками или, если его нет, коротким шаблоном. Поле `contact`
вакансии используется только у HH (контакты из API). Ссылки на отклик из вакансии — кнопками «Откликнуться на hh.ru» / «Откликнуться · сайт», без страницы самой вакансии (она уже есть как «Открыть пост»), повторов и ссылок t.me.

### Адаптация резюме под вакансию

В карточке вакансии при выбранном резюме — блок «Адаптация резюме»: LLM подсказывает,
как переписать **реальный** опыт из резюме под требования вакансии (`POST
/resumes/{id}/tailor/{vacancy_id}`, фоновая джоба `kind=resume_tailor`). Ответ: короткий
вывод, до 8 правок («Было» → «Стало» или «Добавить», раздел резюме, какое требование
закрывает, приоритет; у каждой — «Копировать»), термины вакансии, которые резюме уже
подтверждает, и список «Не добавлять без реального опыта» — требования, которых в резюме
нет. Промпт запрещает выдумывать навыки, работодателей и цифры; недостающие навыки из
сохранённой оценки уходят в этот список, а не в правки.

Механика — как у писем: результат хранится парой `(resume_id, vacancy_id)` в
`resume_tailorings` и отдаётся из БД без вызова LLM, «Пересчитать» — `force=true`, `DELETE`
сбрасывает. Модель — та же, что у писем (`ai.cover_letter_model` → `match_model` →
`model`); смена модели или `RESUME_TAILOR_PROMPT_VERSION` делает результат `stale`. Квота
и отмена — общие для пользовательского LLM. Правка текста резюме сбрасывает его оценки,
письма, адаптации и подготовку к собеседованию.

### Подготовка к собеседованию

В карточке вакансии при выбранном резюме — блок «Подготовка к собеседованию» (`POST
/resumes/{id}/interview-prep/{vacancy_id}`, фоновая джоба `kind=interview_prep`): вопросы,
которые вероятнее всего зададут на этой вакансии, и что ответить. Ответ: короткий вывод,
6–10 вопросов — по технологиям вакансии, по опыту из резюме («расскажите о проекте…»),
поведенческие и по пробелам — у каждого тема, откуда вопрос и до 4 тезисов ответа; до 5
пробелов с советом, что повторить; до 5 вопросов работодателю. Тезисы строятся только из
фактов резюме; для вопроса по пробелу — честная стратегия ответа, а не выдуманный опыт.
Недостающие навыки сохранённой оценки пары модель получает как темы таких вопросов.

Механика — как у адаптации: кэш парой в `interview_preps`, «Пересчитать» — `force=true`,
`DELETE` сбрасывает; модель писем; смена модели или `INTERVIEW_PREP_PROMPT_VERSION` —
`stale`; квота и отмена общие.

**Резюме из файла.** В форме резюме — «Загрузить из файла»: `POST /resumes/parse-file`, тело
запроса — сам файл (PDF или DOCX до 5 МБ, без multipart). Формат определяется по
сигнатуре; PDF читается `pypdf` (текстовый слой, до 30 страниц), DOCX — из
`word/document.xml` стандартной библиотекой. Текст подставляется в поле для правки и не
сохраняется, пока не нажать «Сохранить»; длиннее 50 000 символов — обрезается с пометкой.
Скан без текстового слоя, PDF с паролем и другие форматы — 422 с причиной.

### Аутентификация и per-user данные

Своя лёгкая JWT-аутентификация: argon2-хэш пароля (`pwdlib`) + HS256
(`pyjwt`). Первый зарегистрированный аккаунт становится админом и наследует
резюме/пресеты, созданные до появления пользователей.

- Приватное (по `user_id`): резюме, пресеты фильтров, матчи, письма, адаптации резюме.
- Общее: вакансии, аналитика, курсы ЦБ — единый корпус. Читает любой
  залогиненный пользователь; менять (курсы, кэш LLM) может только админ.
- Только админ: прогоны целиком (запуск, отмена, история, экспорт, SSE), ручной
  импорт и HH sync. Вкладки «Парсинг», «Импорт» и «HH» не-админу не показываются,
  прямой переход по URL уводит на «Вакансии».
- Сессия = короткий access JWT (`JWT_TTL_MINUTES`, 15 мин) + refresh-токен
  (`REFRESH_TTL_DAYS`, 30 дней, скользящий). Access хранится только в памяти
  вкладки и уходит в `Authorization: Bearer …`. Refresh — случайная строка в
  httpOnly cookie `tgjp_refresh` (`SameSite=Strict`, `Path=/api/v1/auth`, в prod
  `Secure`), в БД — только её sha256 (`refresh_tokens`). При загрузке страницы и
  на 401 UI молча вызывает `POST /auth/refresh`, повторяет запрос и на `/login`
  уходит, только если сессии нет — несохранённый ввод не теряется раз в час.
- Каждый refresh ротирует cookie. Повтор уже ротированного значения дольше
  30 с спустя (параллельные вкладки укладываются в это окно) считается кражей:
  отзывается вся сессия (все токены этого входа). `POST /auth/logout` отзывает
  сессию на сервере и стирает cookie; просроченные и отозванные строки чистит
  hourly-очистка служебных таблиц.
- Cookie `SameSite=Strict`, поэтому UI ходит в API того же origin: dev-сервер Vite
  проксирует `/api` на backend (`VITE_API_PROXY_TARGET`), в prod то же делает
  reverse proxy. Если задать `VITE_API_BASE_URL` абсолютным URL, UI и API должны
  остаться same-site: UI на `127.0.0.1`, а API на `localhost` — разные сайты, браузер
  отбросит cookie (`SchemefulSameSiteStrict`), и после перезагрузки придётся входить заново.
- SSE: EventSource не умеет заголовки, а JWT в query оседал бы в логах прокси.
  Поэтому UI перед подключением берёт `POST /auth/sse-ticket` (Bearer + `X-API-Key`)
  и открывает стрим с `?ticket=…`. Тикет — JWT с `typ=sse`: живёт 30 с,
  принимается один раз (использованный `jti` — в Redis `SET NX`, без `REDIS_URL` — в
  памяти процесса) и не годится как access-токен. Автопереподключение EventSource
  с тем же тикетом получит 401 — UI в этом случае дочитывает статус опросом.
  `?access_token=` и `?api_key=` больше не принимаются; curl и Swagger могут слать
  `Authorization: Bearer` (+ `X-API-Key`) прямо в SSE-запрос.
- Swagger (`/docs`) → кнопка «Authorize»: либо вставить готовый JWT в `HTTPBearer`
  (без слова `Bearer`), либо войти в `OAuth2PasswordBearer` — email в поле
  `username`, `client_id`/`secret` пустые (form-эндпоинт `POST /auth/token`, те же
  лимиты, что у `/auth/login`). `X-API-Key` — там же, если задан `API_KEY`.
- Отзыв токенов: в JWT — версия `users.token_version`; `POST /auth/change-password`
  и `POST /auth/logout-all` увеличивают её, и все ранее выданные токены
  (включая SSE и refresh-сессии) перестают приниматься. `is_active=false` отключает пользователя целиком.
- Персональные токены доступа (PAT) — для MCP-сервера и скриптов: страница **Токены**
  (`POST`/`GET`/`DELETE /auth/tokens`). Токен `tgj_…` показывается один раз, в БД — sha256
  (`api_tokens`), срок 1–365 дней (по умолчанию 90), не больше 20 действующих. Передаётся как
  обычный `Authorization: Bearer tgj_…`. Права: `read` (обязателен) — GET-эндпоинты
  пользователя; `llm` — ещё и постановка LLM-задач (оценка резюме, письмо, адаптация,
  подготовка к собеседованию, «Спросить базу», отмена своей задачи) под той же суточной квотой.
  Остальные изменения (резюме, пресеты, пароль) PAT не может, admin-эндпоинты не открывает даже
  у админа, новые токены не выпускает и не отзывает (только из сессии входа). Смена пароля и
  «выйти везде» отзывают и PAT; `last_used_at` обновляется не чаще раза в минуту.
- Перебор паролей: не больше `AUTH_RATE_LIMIT_PER_MINUTE` (20) попыток входа и
  регистрации с одного IP в минуту и `AUTH_MAX_FAILED_LOGINS` (5) неудачных входов
  на email за `AUTH_FAILED_LOGIN_WINDOW_SECONDS` (15 мин); дальше — 429 с
  `Retry-After`, пароль (argon2) не проверяется. С `REDIS_URL` счётчики общие для
  процессов. За NAT/Docker все клиенты могут приходить с одного IP — лимит по IP
  тогда общий.
- Регистрации сериализуются advisory-lock'ом Postgres: два параллельных «первых»
  пользователя не станут оба админами; повтор email → 409 `EMAIL_TAKEN`, формат
  email проверяется (`email-validator`).

Прогон парсинга: API создаёт строку `parse_runs` со статусом `queued` и ставит RQ-джобу (в Docker — `PARSE_JOB_BACKEND=rq`). `parse-worker` claim'ит прогон → `running`, пишет `progress` в БД (+ Redis pub/sub для SSE). Рестарт backend не обрывает воркер: прогресс продолжает обновляться, cancel идёт через `cancel_requested` в БД. Локально без Redis: `PARSE_JOB_BACKEND=inprocess` (ThreadPool в процессе API).

Самовосстановление джоб (parse, LLM и HH sync устроены одинаково):

- **Зависший `running`** (lease истёк — воркер упал или завис) recover-цикл возвращает в `queued` и запускает заново. В режиме `rq` цикл живёт в воркерах, в `inprocess` — в самом API: при старте он сразу поднимает `queued`, оставшиеся от прошлого процесса, а оборванный рестартом `running` — после истечения lease (до ~3 минут при настройках по умолчанию).
- **Отмена.** Прогон, LLM-задача (мэтч, письмо, импорт) и HH sync отменяются флагом `cancel_requested` в БД: задача в очереди сразу получает `cancelled`, выполняемую воркер останавливает в ближайшей точке проверки — импорт перед следующим текстом, HH sync перед следующей страницей поиска или группой деталей (уже полученные вакансии сохраняются, purge listings пропускается), мэтч и письмо после ответа модели (ответ отбрасывается, прежний результат остаётся; если результат уже сохранён — задача `done`). Зависший `running` с запрошенной отменой recover закрывает `cancelled`, а не ставит на повтор. Квота LLM за уже поставленные мэтч/письмо не возвращается.
- **Лимит попыток.** Каждый claim увеличивает `attempts`; прогон, который воркер не довёл до конца `PARSE_JOB_MAX_ATTEMPTS` раз (по умолчанию 3; для LLM-джоб — `LLM_JOB_MAX_ATTEMPTS`, 2; для HH sync — `HH_SYNC_JOB_MAX_ATTEMPTS`, 2), завершается `failed` / `error` с пояснением, а не уходит на очередной круг.
- **Отказ LLM при парсинге.** Транзиентные сбои (5xx, таймаут) повторяются с backoff; после `ai.circuit_breaker_errors` (5) постов подряд с ошибкой срабатывает circuit breaker — LLM отключается до конца прогона, как при исчерпанной квоте, и остальные посты не ждут повторов. 429 определяется по HTTP-статусу ответа.
- **Неполный прогон — `partial`.** Если в `ai.mode: primary` LLM отключился (лимит или circuit breaker), исчерпан потолок вызовов `ai.max_posts_per_run` или доля ошибок LLM выше `ai.max_error_ratio` (10%), часть постов не разобрана. Такой прогон получает статус `partial` с причиной в `error_message`; уже разобранные вакансии сохранены, чекпоинты остаются только у каналов, разобранных до первого потерянного поста, неразобранные посты не кэшируются — повторный прогон обработает их.
- **LLM не запустился в `primary` — `failed`.** Если LLM не удалось запустить (нет ключа, неизвестная модель), прогон в `ai.mode: primary` сразу завершается `failed` — до чтения Telegram, без записи вакансий и чекпоинтов и без повторной попытки; что исправить — в `error_message`. В `assist` прогон в этом случае идёт на правилах с предупреждением.
- **Docker Compose:** у сервисов приложения `restart: unless-stopped` и healthcheck; воркеры стартуют после того, как backend стал healthy (то есть применил миграции).
- **Миграции под замком.** `alembic upgrade head` при старте выполняется под `pg_advisory_lock`: второй процесс или реплика API ждёт, пока первый применит миграции, вместо гонки DDL.
- **Пул соединений по роли процесса.** API — 20 + 20 overflow на все процессы API вместе (`API_WORKERS=4` → 5 + 5 у каждого; потоков threadpool у процесса столько же, сколько соединений), `parse-worker` — 4 + 12 (LLM-потоки прогона ходят в AI-кэш), `llm-worker`, `hh-worker` и `maintenance-worker` — 2 + 2. Так `--scale llm-worker=4` укладывается в `max_connections=100` Postgres. Переопределение — `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`; фактические значения — метрики `db_pool_*` (при нескольких процессах — сумма).
- **Защита от перегрузки.** Процесс API обрабатывает одновременно не больше запросов, чем у него соединений с БД (при `API_WORKERS=4` — 10). Остальные ждут в очереди процесса до `API_QUEUE_TIMEOUT_SECONDS` (2 с), после чего получают 503 `OVERLOADED` с `retryable: true` и `Retry-After: 1`; в HTTP-журнале это WARNING, а не ERROR. Без лимита всплеск нагрузки приводил к тупику: sync-эндпоинт проходит через threadpool несколько раз и держит соединение между переходами, так что потоки ждали соединения, а соединения — потоки. API зависал целиком, вместе с `/health`, на минуты. `/health` очередь не проходит, SSE-стрим отдаёт место сразу после начала ответа. Ожидание соединения из пула у API — 5 с (`DB_POOL_TIMEOUT`), у воркеров 30 с. UI повторяет retryable-ошибки (`retryIfRetryable` в `src/api/client.ts`).
- **Несколько процессов API.** `API_WORKERS` (в compose — 4) запускает столько процессов uvicorn на одном порту: один процесс Python под GIL использует ~1 ядро. Нужны `REDIS_URL` (лимиты входа и одноразовость SSE-тикетов), `JWT_SECRET` (иначе у каждого процесса свой эфемерный секрет) и `rq` у всех задач — без них API не стартует и называет переменную. Общую работу — очистку при старте и раз в час, синхронизацию курсов, сервер `/metrics` — выполняет один процесс-лидер (`pg_try_advisory_lock` на своём соединении, `backend/leader.py`); если он упал, роль за ≤30 с берёт другой процесс или перезапущенный uvicorn воркер. `/metrics` лидера суммирует метрики всех процессов (multiprocess-режим prometheus_client). `uvicorn backend.main:app --reload` всегда один процесс.
- **Фоновое обслуживание каталога** (`backend/maintenance.py`): индексация эмбеддингов и оценки зарплат, недельный обзор рынка (LLM) и карта рынка (t-SNE — до минуты CPU на 8 тыс. точек). При `MAINTENANCE_BACKEND=worker` (в compose) их выполняет отдельный сервис `maintenance-worker`: задачи не отнимают у запросов API CPU и соединения пула, число мест под запросы которого равно размеру пула. Реплик может быть несколько — работает одна (advisory lock), задачи идут по очереди, цикл раз в 10 с; heartbeat бьёт между циклами, поэтому порог healthcheck и watchdog — 1 ч. Без воркера (`inprocess`, по умолчанию: uvicorn локально, тесты) задачи выполняет лидер API, каждую в своём потоке. Пересчёт карты по кнопке админа — запрос в `maintenance_requests` (миграция 051), его подхватывает тот же исполнитель.
- **Liveness воркеров.** Healthcheck воркера проверяет не ответ порта, а возраст heartbeat в `/metrics` (`worker_heartbeat_timestamp_seconds`): его обновляют цикл RQ (в простое раз в 45 с) и продление lease выполняемой джобы. Старше `WORKER_HEARTBEAT_MAX_AGE_SECONDS` (180 с) — `unhealthy`. Docker unhealthy-контейнер сам не перезапускает, поэтому воркер, чей heartbeat молчит дольше `WORKER_STALL_EXIT_SECONDS` (900 с), завершается сам, restart policy поднимает его, а recover возвращает джобу в очередь.

SSE (`/runs/{id}/events`, `/llm-jobs/{id}/events`, `/hh/sync-jobs/{id}/events`): один подписчик `redis.asyncio` на процесс API раздаёт события всем стримам — соединения не занимают потоки, а БД читается вне event loop. Каждые 15 с тишины стрим шлёт комментарий `: ping` (прокси не рвут соединение по idle-timeout), раз в 5 с сверяет статус с БД на случай пропущенного `done`. Без Redis или при его сбое стрим переходит на опрос БД и живёт до терминального статуса.

Потоковая обработка прогона: каналы читаются в фоновом потоке, и каждый прочитанный канал сразу уходит в разбор (rules → LLM → дедуп → UPSERT), не дожидаясь остальных. Очередь между вычиткой и разбором рассчитана на `parser.channel_concurrency` каналов: если разбор (обычно LLM) отстаёт, вычитка ждёт. В памяти держится несколько каналов, а не всё окно прогона, и сбой посреди вычитки не теряет уже разобранное. Пока идёт вычитка, прогресс показывает фазу `fetching` и число прочитанных каналов; общее число постов при этом растёт.

Инкрементальная вычитка каналов:

- **Чекпоинты.** Для каждого канала, прочитанного сплошь до границы окна, сохраняется чекпоинт «прочитано всё с даты X по сообщение N» (`telegram_channel_checkpoints`). Следующий прогон читает из канала только сообщения новее N — ежедневный запуск не перечитывает недельное окно заново. Чекпоинт пишется сразу, как только посты канала разобраны и записаны в БД, поэтому прогон, перезапущенный после падения воркера, не перечитывает готовые каналы. Чекпоинт не двигается, если канал прочитан не до конца или его вакансии не записались; после первого поста, потерянного из-за LLM (в `primary` — сбой LLM на посте, вне `assist` — отключение LLM), чекпоинты до конца прогона больше не двигаются. Полный перечит окна (после смены фильтров или промпта) — галочка «Перечитать окно дат целиком» в форме запуска. Подробности — `parser.incremental_fetch` в [config.md](config.md).
- **Окно в прошлом.** Если `date_to` раньше сегодняшнего дня, обход начинается с `date_to` (`offset_date`), а не перебирает всё, что новее окна, расходуя `max_posts_per_channel`.
- **FloodWait.** Ожидание до `parser.flood_wait_max_seconds` пережидается с продолжением обхода с места остановки; более долгое или ошибка посреди канала возвращают уже прочитанные посты с предупреждением, а не пустой канал.
- **Паузы между страницами.** `parser.sleep_between_requests_seconds` (по умолчанию `1`) — страницы истории канала (100 сообщений) запрашиваются не чаще раза в N секунд; сколько она стоит, видно в логе канала, в span `telegram.channel` и в `telegram_request_pause_seconds_total`.
- **Дедуп** сравнивает fuzzy только в блоках, где вакансия могла бы оказаться: тот же набор специализаций (`parser.fuzzy_dedup_block_by_specializations`), та же компания или тот же контакт — почти-дубль с по-другому извлечёнными специализациями находится по компании или контакту. Снимок прогресса несёт последние 30 вакансий, а не копию всех уникальных.
- **Перепост с правками.** Кроме составного ключа (он сравнивает и зарплату) пост сравнивается по полному нормализованному тексту (RapidFuzz `ratio` не ниже `parser.fuzzy_text_duplicate_threshold`, 95) с вакансиями прогона и с вакансиями Telegram из БД за `parser.cross_run_dedup_days` (40) дней. Разные известные грейды, разные компании, непересекающиеся роли или языки программирования — разные вакансии (шаблон компании: junior и senior, аналитик и разработчик, Java и Python почти одним текстом), посты дальше 40 дней друг от друга не сравниваются. Совпавший пост — появление известной вакансии с причиной `fuzzy_text:<score>`: она, как при точном перепосте, получает более позднюю дату поста, возвращается из архива и привязывается к прогону; новой вакансии не появляется. HH и ручной импорт в этом не участвуют.
- **Чистка сохранённых вакансий** по позже появившимся правилам — разово: `python -m jobdesk.cli db clean-vacancies` показывает, что удалит (посты соискателей и подборки — они не вакансии, удаление каскадом убирает оценки, письма и эмбеддинги) и какие технологии перепишет, `--apply` применяет.
- **Накопленные почти-дубли** (до дедупа между прогонами) склеиваются разово: `python -m jobdesk.cli db merge-duplicates` показывает пары, `--apply` склеивает. Более поздняя копия помечается дублем (`is_duplicate`, `duplicate_of` — исходная) и пропадает из списков и аналитики, её появления и прогоны переходят к исходной; строка и оценки с письмами к ней остаются.

### MCP-сервер (Claude Desktop / Claude Code)

`jobdesk_mcp` — MCP-сервер по stdio: даёт Claude инструменты поверх API, чтобы в чате искать
вакансии, смотреть рынок для своего резюме, получать оценку и письмо. Это клиент HTTP API с
персональным токеном: авторизация, квоты LLM и защита от перегрузки остаются на стороне API,
а `backend` и ядро он не импортирует.

```bash
# зависимость mcp — отдельный extra (в образ backend не входит)
poetry install --extras mcp          # или: pip install -e ".[mcp]"

# 1. Токен: UI → «Токены» → «Создать токен» (для оценки и писем — отметить LLM-задачи)
# 2. Claude Code (из корня проекта):
claude mcp add jobdesk -e JOBDESK_TOKEN=tgj_... -- .venv/Scripts/python.exe -m jobdesk_mcp
```

Claude Desktop — `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "jobdesk": {
      "command": "C:\\path\\to\\jobdesk\\.venv\\Scripts\\python.exe",
```

Env: `JOBDESK_TOKEN` (обязателен), `JOBDESK_API_URL` (по умолчанию
`http://127.0.0.1:9000/api/v1` — API из compose), `JOBDESK_API_KEY` (если у API задан
`API_KEY`), `JOBDESK_LLM_WAIT_SECONDS` (сколько ждать LLM-задачу, по умолчанию 60).

| Группа | Инструменты |
|---|---|
| Поиск | `list_filter_values` (роли, грейды, форматы, частые технологии), `search_vacancies` (текст или смысл, фильтры, пресет, сортировка по дате / зарплате / оценке / близости к резюме, до 20 карточек), `get_vacancy` (текст, контакты, флаги, рыночная вилка), `similar_vacancies`, `vacancy_history`, `company_profile`, `list_filter_presets` |
| Рынок | `salary_stats`, `technology_trends`, `market_digest` |
| Резюме | `list_resumes`, `get_resume`, `resume_market`, `resume_skill_gaps`, `resume_what_if`, `resume_career_paths` |
| LLM (квота) | `match_resume`, `match_resume_batch`, `cover_letter`, `tailor_resume`, `interview_prep`, `ask_market`, `get_llm_job` |

Ответы — компактный JSON (без пустых полей, списки до 20, превью до 300 символов, полный текст
до 4000). Текст вакансии обёрнут в маркеры «данные, не инструкции»: посты из открытых каналов
могут содержать prompt-injection. LLM-инструмент берёт готовый результат из кэша бесплатно,
иначе ставит задачу и ждёт её до `JOBDESK_LLM_WAIT_SECONDS`; не успела — возвращает `job_id`
для `get_llm_job`. Прерванный клиентом вызов отменяет задачу. Ошибки API приходят модели
текстом с подсказкой (токен отозван, нет права LLM, эмбеддинги недоступны, API не запущен).

`POST /vacancies/import`, `/vacancies/reextract`, `POST /fx/*`, `POST /ai-cache/clear` и HH.
`API_KEY`, если задан, — дополнительный заголовок `X-API-Key` поверх JWT, а не замена ему.

Query-параметры списка, метрик, аналитики и экспорта типизированы на уровне FastAPI:
`page` 1…10 000, `page_size` 1…500 (списки листаются только до 10 000-й позиции: дальше OFFSET дорог, 422 с просьбой уточнить фильтры), даты — `YYYY-MM-DD` (пустое значение = не задано), `q` до 500
символов; нарушение — 422 `VALIDATION` с описанием поля, а не 500. Тексты в телах ограничены:
резюме — 50 000 символов, вакансия в импорте — 30 000.

Тело `POST /runs` — whitelist overrides поверх `config.yaml`: `channels`,
`search.date_from|date_to`, `filters.*`,
`parser.vacancy_score_threshold|vacancy_min_substantive_score|incremental_fetch`,
`ai.enabled|model|fallback_models|use_cache` (модели — только id из `llm_models.yaml`).
Любое другое поле → 422: `ai.base_url`, лимиты, concurrency и путь к Telethon-сессии
задаются только на сервере.

Импортированные вручную вакансии помечаются `source_channel = "manual"`
(по нему их можно отфильтровать в списке); дедупликация — по тому же хэшу
текста, что и у постов Telegram. Пост-фильтры прогона (exclude_keywords,
форматы, локации) и порог `vacancy_score` при импорте не применяются:
при включённом AI решение «вакансия или нет» принимает LLM (`is_job_post`),
без него текст сохраняется как есть.

`POST /vacancies/import` без LLM (AI выключен или все тексты уже в базе) отвечает
сразу 200 с итогом. Если нужен LLM — 202 `{job_id}`: разбор идёт LLM-джобой
`kind=import` (та же очередь, lease, recover и SSE, что у мэтчинга), до 50 вызовов
модели не держат HTTP-запрос и транзакцию. Итог по каждому тексту пишется в
`llm_jobs.result` по мере обработки: `GET /llm-jobs/{id}` отдаёт его в
`import_result` ещё до завершения (страница «Импорт» показывает «N из M»), а
ретрай после падения воркера продолжает с первого необработанного текста. Импорт
занимает один слот `ai.interactive_per_user_limit`; таймаут RQ — базовый плюс
60 с на текст.

`POST /vacancies/reextract` — та же механика для уже сохранённых вакансий
(`kind=reextract`, итог в `reextract_result`): миграция 037 вынесла языки из
специализаций в технологии, и у вакансий вида `["Go"]` роли не осталось. Цели —
активные вакансии не из HH с пустыми `detected_specializations`, до 500 за джобу
(свежие первыми); LLM разбирает их текст заново (текущий `EXTRACT_PROMPT_VERSION`, кэш
прежней версии не используется), результат пишется тем же UPSERT, что у прогона. Ответ «не
вакансия» строку не удаляет (`kept`). Одновременно идёт одна такая джоба — повторный
`POST` возвращает её `job_id`. Кнопка — на странице «Импорт».

Если LLM в воркере не запустился (нет ключа, неизвестная модель), импорт-задача
завершается `error` с причиной, а тексты не сохраняются: без LLM нет проверки
«это вакансия?». Итог по уже обработанным текстам остаётся в `result`. Исчерпанная
суточная квота пользователя, наоборот, не ошибка — остаток текстов разбирается
правилами. В `ai.mode: primary` текст сверх `ai.max_posts_per_run` получает
статус `error` с причиной и не сохраняется.

Пока страница «Импорт» ждёт фоновую задачу, рядом с кнопкой разбора есть
«Отменить» (`POST /llm-jobs/{id}/cancel`): импорт останавливается перед следующим
текстом, уже разобранные тексты остаются в базе, страница показывает итог по ним
и пометку об отмене; текст в поле не очищается.

Вакансии с HH (`source_channel = "hh"`) появляются после admin-sync
(`/hh` или `POST /hh/sync`). Sync — фоновая durable-джоба (`hh_sync_jobs`,
lease и recover как у прогонов; в Docker — `hh-worker`, без Redis —
`HH_SYNC_JOB_BACKEND=inprocess`): до ~2000 detail-запросов при 3 rps идут
10+ минут, внутри HTTP-запроса их обрывал бы прокси. Страница `/hh` показывает
ход и итог последнего sync и после перезагрузки; идущий sync можно отменить
кнопкой «Отменить» (`POST /hh/sync-jobs/{id}/cancel`) — итог до отмены сохраняется.
HH отдаёт не глубже 2000 вакансий на поиск: если найдено больше, в `warnings` итога
(и на странице `/hh`) — предупреждение сузить окно или запрос. Если повторная загрузка
деталей не удалась, сохранённая карточка не меняется (ошибка — в `errors`); вакансия
без профессиональных ролей получает пустой список специализаций. Поля берутся из API без LLM, дедуп мультигорода
как в MVP hhparser, TTL вакансий — общий `retention.vacancy_ttl_days`
(soft-archive: строки остаются в БД для исторических метрик).
Грейд HH мапится из `experience.id`: `noExperience`→`intern`,
`between1And3`→`junior`, `between3And6`→`middle`, `moreThan6`→`senior`
(при старте/hourly cleanup — идемпотентный бэкфилл по `required_experience`).
Роли HH «Тестировщик» и «Программист, разработчик» пишутся в
`detected_specializations` сразу как `QA` / `Software Engineer`.
На вкладке `/hh` окно sync задаётся в интерфейсе: All, 7 / 14 / 30 дней или диапазон дат.
Кэш короткой выдачи (`hh_listings`) живёт `hh.listing_ttl_days` и не даёт
повторно дергать detail для уже загруженных id.

Кэш ответов LLM хранится в PostgreSQL (`ai_extraction_cache`). Параметры в `config.yaml`: `ai.cache_backend: postgres`, `ai.cache_ttl_days` (0 — без срока, иначе дни; по умолчанию 45). Просроченные записи и записи от прежних версий промпта удаляет почасовая фоновая очистка. Очистка — кнопка на странице **Парсинг** или `POST /ai-cache/clear`. Адаптер Postgres регистрируется при старте backend/CLI (порт `AIExtractionCacheBackend` в core, без зависимости `jobdesk` → `backend`).

| `vacancy_embeddings` / `resume_embeddings` | Эмбеддинги (pgvector `vector(1536)`, HNSW по косинусу у вакансий), `model` + `content_hash` — для переиндексации |
| `users` | Аккаунты: email, argon2-хэш, `is_admin` |
| `telegram_channel_checkpoints` | Чекпоинт канала для инкрементальной вычитки: `last_message_id`, `covered_from` |
| `llm_user_usage` | Вызовы LLM пользователя за сутки — квота `LLM_USER_DAILY_CALLS` |
| `refresh_tokens` | Refresh-сессии: sha256 токена, семья (один вход), ротация и отзыв |
| `idempotency_keys` | Сохранённые ответы мутаций по `Idempotency-Key` (TTL) |
| `parse_run_vacancies` | Какие вакансии встретил прогон (история и экспорт прогона) |
| `vacancy_sightings` | Каждое появление поста Telegram: оригинал или дубль со ссылкой на вакансию |
| `vacancy_salary_estimates` | Ориентировочная зарплата вакансий без вилки (медиана, p25–p75, соседи); пересчитывает фоновое обслуживание |

Служебные таблицы чистятся сами (при старте и раз в час): просроченный кэш LLM и ключи идемпотентности, завершённые LLM-джобы старше `retention.llm_jobs_ttl_days` (30) и прогоны старше `retention.parse_runs_ttl_days` (180) — см. [config.md](config.md). Вакансии только архивируются, не удаляются.

**Если меняете колонки/таблицы** — добавьте новую миграцию (`alembic revision`) и обновите модели в `backend/db/models.py`; при следующем `docker compose up` она применится автоматически, данные сохранятся.

Ядро парсинга (`jobdesk.parse_runner` + общий `jobdesk.ingestion`) вызывается из `backend/workers/parse_tasks.py` (`run_service` только ставит прогон в очередь); результаты пишутся в PostgreSQL (UPSERT по `id` вакансии). Ручной импорт использует тот же ingestion с `MANUAL_POLICY`.

## Telethon: что подготовить локально

**Не передавайте никому** `api_hash`, коды SMS и файл сессии. Держите их только в `.env` и в `sessions/` (каталог в `.gitignore`).

1. Зарегистрируйте приложение на [https://my.telegram.org/apps](https://my.telegram.org/apps) и получите **API ID** и **API hash**.
2. Создайте `.env` рядом с `config.yaml` (образец в `.env.example`).
3. В `config.yaml` укажите `telegram.telethon_session_file` (например `sessions/tg_jobs.session`).
4. **Первый запуск** — интерактивная авторизация (см. [Docker](#первая-авторизация-telethon) или CLI ниже).

### Сообщения в консоли при первом запуске

- **`Failed to load SSL library` / `cryptg module not installed`** — на Windows Telethon может работать без cryptg; для ускорения: `poetry install --extras telethon`.
- **`Please enter your phone`** — первая авторизация. В `.env` можно задать **`TELEGRAM_PHONE`**; код из SMS вводится один раз (или **`TELEGRAM_2FA_PASSWORD`** при 2FA).

## Установка без Docker (Poetry)

```powershell
cd путь\к\jobdesk
poetry install
poetry install --extras telethon   # cryptg (опционально)
poetry install --extras ai         # OpenRouter
```

**Версии зависимостей фиксирует `poetry.lock`.** Docker-образ backend ставит их из lock-файла: `poetry export` → `pip install --require-hashes`, затем проект `--no-deps` и `pip check`. Поэтому в контейнере те же версии, что локально и в тестах, а не самые свежие из диапазонов `pyproject.toml`. Новая зависимость: `poetry add <pkg>`, обновление: `poetry update <pkg>`. Оба коммитятся вместе с `poetry.lock`, а `poetry lock` без `--regenerate` уже залоченные версии не поднимает.

Проверка:

```powershell
poetry run python -c "import telethon; print(telethon.__version__)"
```

Используйте **`poetry run python -m jobdesk.cli …`** или активируйте `.venv`.

## Конфигурация

Основной файл: `config.yaml` (схема: `jobdesk/config/schema.py`).

Полное описание секций — в [config.md](config.md).

### Отбор постов (`parser`)

- **`vacancy_score_threshold`** — минимальный общий score правил по шкале 0–100 (как у HH, там всегда 100).
- **`vacancy_min_substantive_score`** — минимум без бонуса за email/@ (отсекает «пустые» контакты).
- Пост соискателя (`#resume`, `#cv`, `#ищуработу`, `#opentowork`, «ищу работу»; хэштег соискателя не
  считается, если рядом `#вакансия`/`#vacancy`/`#hiring`) и подборка вакансий («Подборка вакансий»,
  «Ещё 14 вакансий дня», «Дайджест вакансий», `#дайджест`) получают score 0 всегда — до LLM не доходят.
  Курсы, обучение, школа, менторство, «резюме» обнуляют score, только если в посте нет ни маркеров
  найма, ни названия роли: «присылайте резюме» и «оплачиваем обучение» есть в обычных вакансиях
  (`jobdesk/extraction/vacancy_detector.py`).
- **`channel_concurrency`** — сколько каналов опрашивать параллельно в одной
  Telethon-сессии (`1` — последовательно; слишком большое значение повышает риск FloodWait).
  Это же размер очереди прочитанных, но ещё не разобранных каналов.
- **`db_flush_every_posts`** / **`db_flush_pending_vacancies`** — промежуточный
  UPSERT в БД во время прогона (backend), чтобы при обрыве не терять уже
  обработанные уникальные вакансии.

### Хранение вакансий (`retention`)

- **`vacancy_ttl_days`** (по умолчанию 40) — через сколько дней вакансия
  архивируется (soft delete, `archived_at`): по `post_date`, а без неё — по
  `parsed_at`. `0` — не архивировать. Проверка идёт при старте backend, раз в
  час фоном и после каждого прогона. Архивные строки не попадают в списки,
  пока не передать `include_archived=true`. Вкладка **Аналитика** по умолчанию
  включает архив (активные + архивные), в т.ч. для YoY/MoM по каналу `hh`;
  флажок «Учитывать архивные вакансии» его отключает.
  Повторная публикация возвращает вакансию из архива: если канал снова
  запостил тот же текст (или HH обновил `published_at`), `post_date`
  сдвигается на свежую дату и TTL отсчитывается от неё.

### HH.ru (`hh`)

- **`enabled`** — разрешить admin sync.
- **`listing_ttl_days`** (по умолчанию 40) — TTL кэша `hh_listings` (hard delete
  по `last_seen_at`); после purge detail снова запросится.
- **`search.text` / `professional_role` / `per_page`** — параметры выдачи
  (дефолт — AQA/Python, роли 124 и 96).
- **`max_rps`** — лимит запросов к API (по умолчанию 3).
- **`db_flush_batch_size`** (по умолчанию 30) — промежуточный UPSERT+commit;
  буфер Vacancy в памяти очищается после каждого батча (меньше RAM, прогресс
  не теряется при обрыве/429).
- Секреты: `HH_API_TOKEN`, `HH_CONTACT_EMAIL` в `.env` (и в docker через `env_file`).
- Метрики/дашборд: Grafana «HH.ru sync» (`observability/grafana/.../hh.json`).

### Секция `ai` (опционально)

По умолчанию **`ai.enabled: false`**. При включении — разбор через **OpenRouter** (OpenAI-compatible SDK).

| Поле | Назначение |
|------|------------|
| `enabled` | Включить LLM |
| `mode` | `assist` — LLM уточняет поля правил; `primary` — LLM основной источник, без LLM пост не разбирается. Какие поля откуда берутся — [config.md](config.md#как-llm-и-правила-делят-поля-mode) |
| `merge.prefer_ai_for`, `merge.min_confidence` | `assist`: в каких полях и с какой уверенностью LLM перекрывает правила |
| `model` | Id из `llm_models.yaml` — модель парсинга вакансий |
| `match_model` | Модель матчинга резюме ↔ вакансия (обычно reasoning). Пусто — берётся `model` |
| `match_reasoning_enabled` | `true`, если `match_model` — reasoning-модель (OpenRouter `reasoning` вместо `json_object`) |
| `match_reasoning_effort` | Уровень рассуждений матчинга и писем: `max` / `xhigh` / `high` / `medium` / `low` / `minimal` / `none`. Только при `match_reasoning_enabled: true`; пусто — дефолт модели. Неподдерживаемый уровень OpenRouter сводит к ближайшему (напр. Gemini 3: `xhigh` → `high`); модели без выбора уровня его игнорируют. Рассуждения расходуют `max_completion_tokens` — на `xhigh`/`max` лимит стоит поднять |
| `cover_letter_model` | Модель генерации сопроводительных писем. Пусто — `match_model`, затем `model` |
| `fallback_models` | Запасные модели |
| `concurrency`, `requests_per_minute` | Темп и параллелизм парсинга |
| `interactive_concurrency`, `interactive_per_user_limit` | Пул потоков фоновых мэтч/письмо/импорт — только при `LLM_JOB_BACKEND=inprocess` (при `rq` параллелизм = число реплик `llm-worker`); лимит активных LLM-джоб на пользователя — в обоих режимах |
| `stop_llm_when_rate_limited` | Отключить LLM при 429 до конца прогона. В `mode: primary` оставшиеся посты не разбираются, и прогон завершается `partial` (см. «Самовосстановление джоб») |
| `circuit_breaker_errors` | Столько постов подряд с ошибкой LLM — и LLM отключается до конца прогона (по умолчанию 5, `0` — выключен) |
| `max_error_ratio` | `mode: primary`: доля ошибок LLM, выше которой прогон — `partial` (по умолчанию 0.1) |
| `max_retries_on_error` | Повторы при транзиентном сбое — 5xx, таймаут, обрыв соединения (по умолчанию 2, backoff 2/4/8… с; `0` — без повторов). Действует для парсинга, матчинга и писем |
| `max_completion_tokens` | Лимит выходных токенов |
| `use_cache` | Дисковый/Postgres кэш LLM |
| `prompt_version` | Должен совпадать с `EXTRACT_PROMPT_VERSION` в коде; кэш ключуется константой |

Ключ в `.env`: `OPENROUTER_API_KEY=sk-or-v1-...`

#### Eval моделей эмбеддингов

Сравнивает модели `ai.embeddings.model` на своих вакансиях в размерности 1536 (как колонка
`vector(1536)`); основную БД только читает. Задачи и метрики:

| Задача | Разметка | Метрики |
|---|---|---|
| Смысловой поиск | LLM пишет по вакансии запрос соискателя (keywords + natural) | MRR@10, Recall@1/10/50 исходной вакансии, доля той же роли в top-10 |
| Поиск с судьёй | ручные запросы `evals/golden/embedding_queries.jsonl` + выборка синтетических; пул top-10 всех моделей оценивает LLM (0/1/2) | nDCG@10, Precision@10 |
| «Похожие» | роли и грейды из разбора | совпадение роли/грейда у 10 соседей, тройки с трудным негативом (тот же стек, другая роль), силуэт по ролям |
| Дубли | скрытые копии → оригинал | Recall@1; пересчёт порога `NEAR_DUPLICATE_DISTANCE` под модель |
| Подбор под резюме | LLM-оценки матчей (`overall_score`) | Spearman косинуса и оценки |

```powershell
.venv\Scripts\python.exe scripts\build_embedding_eval.py                      # выгрузка (READ ONLY)
.venv\Scripts\python.exe -m jobdesk.evals.embeddings queries --n 150   # синтетические запросы (LLM)
.venv\Scripts\python.exe -m jobdesk.evals.embeddings run               # векторы + судья + отчёт
```

Варианты моделей — `VARIANTS` в `jobdesk/evals/embeddings/embedder.py` (в т.ч. с инструкцией
для запроса у Qwen3). Векторы и оценки судьи кэшируются в `evals/embeddings/` (в `.gitignore`: тексты
вакансий и резюме), отчёт — `evals/reports/embeddings_<ts>.md`.

> **Приватность:** текст постов уходит на серверы OpenRouter/провайдера модели.

### Резервное копирование (pg_dump по расписанию)

Сервис `pg-backup` в `docker-compose.yml` (входит в ядро, не в профиль observability)
раз в `BACKUP_INTERVAL_HOURS` (по умолчанию 24) снимает `pg_dump -Fc` **всей** базы —
пользователи, резюме, матчи, письма, пресеты, HH, чекпоинты каналов, квоты LLM.
Логика — `scripts/pg_backup.sh`.

- **Проверка восстановления — на каждом дампе.** Дамп восстанавливается во временный
  кластер внутри контейнера (боевой Postgres не нагружается), затем сверяются набор
  таблиц и `alembic_version` с источником; таблица, где в источнике есть строки, а после
  восстановления пусто, — провал. Не прошедший проверку дамп остаётся как
  `*.dump.unverified`, повтор — через `BACKUP_RETRY_MINUTES` (60).
- **Где лежит.** `BACKUP_HOST_DIR` на хосте (по умолчанию `./backup/pg`, в `.gitignore`):
  `tgjobs_<UTC-время>.dump` + `.counts` (число строк по таблицам после восстановления).
  Каталог на хосте переживает `docker compose down -v`, но не потерю диска — копию за
  пределы машины нужно настроить отдельно.
- **Ротация.** Хранятся последние `BACKUP_KEEP` (7) проверенных дампов.
- **Мониторинг.** Контейнер `unhealthy`, если последний проверенный дамп старше
  1,5 × `BACKUP_INTERVAL_HOURS`; каждый шаг пишется в stdout (в Loki через Alloy).
  Рестарт контейнера дамп не повторяет — отсчёт идёт от последнего удачного.
- **Метрики для алертов.** При старте и после каждой попытки скрипт перезаписывает
  `pg_backup.prom` в каталоге дампов (текстовый формат Prometheus):
  `pg_backup_last_verified_timestamp_seconds` (0 — проверенного дампа нет),
  `pg_backup_interval_seconds`, `pg_backup_last_attempt_timestamp_seconds` и
  `pg_backup_last_attempt_success` (1/0). Итог попытки хранится в `.last_attempt` и
  переживает рестарт; запуск, не получивший lock, попыткой не считается. В профиле
  observability файл читает Alloy, на нём построены алерты `PgBackupStale`,
  `PgBackupFailed` и `PgBackupMetricsMissing` (см. «Алерты»).

```powershell
# внеплановый дамп сейчас
docker compose exec pg-backup /scripts/pg_backup.sh once
# проверить восстановление существующего дампа (любого, в т.ч. снятого вручную)
docker compose exec pg-backup /scripts/pg_backup.sh check /backups/tgjobs_20261015_030000.dump
```

**Восстановление** — в пересозданную базу: `pg_restore --clean` поверх существующей
оставил бы таблицы из миграций новее дампа, и `alembic upgrade` при старте упал бы.

```powershell
docker compose stop backend parse-worker llm-worker hh-worker maintenance-worker
docker compose exec pg-backup dropdb --force tgjobs
docker compose exec pg-backup createdb tgjobs
docker compose exec pg-backup pg_restore -d tgjobs --no-owner --exit-on-error /backups/tgjobs_20261015_030000.dump
docker compose start backend parse-worker llm-worker hh-worker maintenance-worker
```

Backend при старте догонит схему миграциями, если дамп старше кода.

```powershell
poetry run jobdesk db import -f backup/jobdesk_dump.json
# полная замена данных в целевой БД (с подтверждением):
poetry run jobdesk db import -f backup/jobdesk_dump.json --mode replace
```

По умолчанию `--mode merge` — UPSERT по первичному ключу (существующие строки обновляются).  
`replace` — сначала очищает таблицы дампа (прогоны, курсы, вакансии, связки прогон–вакансия,
появления, кэш LLM), затем загружает дамп. Вместе с вакансиями каскадом удаляются оценки
соответствия, письма и LLM-задачи пользователей по вакансиям — в дамп они не входят;
подтверждение называет, сколько их удалится.

Логи: консоль + `logs/app.log` (в Docker — только stdout, их собирает Alloy в Loki). Запись асинхронная: `QueueHandler` на root кладёт запись в очередь, stdout/файл пишет фоновый `QueueListener` — логирование не блокирует event loop. `app.log` ротируется по 10 МБ, хранится 5 частей `app.log.N.gz`. Stdout контейнеров в `docker-compose.yml` — `json-file` с ротацией (5 × 10 МБ, сжатие ротированных частей).

## Результаты и экспорт

- **PostgreSQL** — постоянное хранение уникальных вакансий и журнал прогонов (`parse_runs`).
- **Экспорт из UI** — `GET /runs/{id}/export.xlsx` и `.json` (листы и метрики как в `exporters/`).
- **Потолок экспорта.** xlsx списка и прогона и JSON прогона выгружают не больше `EXPORT_MAX_ROWS` вакансий (по умолчанию 50 000) в текущей сортировке. Если под фильтр попало больше, в листе `metrics_summary` появляется строка `truncated` («обрезано до N из M»), в ответе — заголовок `X-Export-Truncated: N/M`, а UI показывает предупреждение. xlsx пишется потоком (openpyxl `write_only`, строки читаются из БД одним запросом порциями) — в памяти не держится весь корпус.

## Observability (Prometheus + Grafana + Loki)

Стек метрик/логов/трасс поднимается вместе с приложением, если в `.env`
задан `COMPOSE_PROFILES=observability` (дефолт из `.env.example`):

| Компонент | Назначение |
|-----------|------------|
| **`prometheus-fastapi-instrumentator`** | Счётчики запросов, статус-коды, latency на backend |
| **`GET /metrics`** | Эндпоинт Prometheus на отдельном порту `API_METRICS_PORT` (`backend:9100`, только Docker-сеть; не путать с `/api/v1/vacancies/metrics`) |
| **Prometheus** | Scrape backend, llm-worker, parse-worker, hh-worker и maintenance-worker каждые 15 с (`observability/prometheus.yml`); правила алертов — `observability/alerts/` |
| **Alertmanager** | Сработавшие алерты (см. «Алерты»); наружу не отправляет — UI `:9093` и Grafana → Alerting |
| **Grafana** | Дашборды **API**, **LLM**, **LLM jobs / queue**, **Pipeline**, **Parse run**, **HH.ru sync**, **DB pool** |
| **`llm_*` метрики** | Вызовы OpenRouter, токены, latency, кэш и пропуски при AI-enrichment; ожидание RPM-лимита (`llm_rate_gate_wait_seconds`), повторы (`llm_retries_total{reason}`), оценка стоимости по ценам `llm_models.yaml` (`llm_cost_usd_total{model}`), отключение LLM посреди разбора — раз за прогон или импорт (`llm_enrich_disabled_total{reason}`: `circuit_breaker`, `quota`, `init_failed`) |
| **Метрики прогона** | Живые, во время прогона: каналы и посты Telegram (`telegram_channels_fetched_total{result}`, `telegram_posts_fetched_total`, `telegram_channel_fetch_duration_seconds`), паузы между страницами истории (`telegram_request_pause_seconds_total`), FloodWait — в т.ч. короткие, которые Telethon пережидает сам (`telegram_flood_waits_total{handled_by}`), поток обработанных постов (`parse_posts_processed_total{result}`), длительность фаз (`parse_phase_duration_seconds{phase}`) |
| **Доменные метрики** | прогоны, UPSERT/TTL, импорт, матчинг, письма, LLM-джобы (`llm_job_enqueue_*`, `llm_worker_*`, `llm_jobs_by_status`, recover), глубина RQ-очередей (`llm_rq_queue_jobs{queue="llm"|"parse"}`), parse recover (`parse_jobs_recover_total`), отказы 503 `OVERLOADED` (`api_overload_rejections_total`; 503 от HH сюда не входят), auth, ЦБ |
| **`db_*` gauges** | COUNT-агрегаты по таблицам с кэшем `METRICS_DB_STATS_CACHE_SECONDS` (30 с) между scrape (вакансии, резюме, матчи, письма, прогоны, LLM-кэш, свежесть курсов ЦБ, задачи в `running` с истёкшим lease — `db_jobs_lease_expired{kind="parse"|"llm"|"hh_sync"}`); только на backend (`job="jobdesk-backend"`) |
| **`db_pool_*` gauges** | SQLAlchemy QueuePool: занято / свободно / overflow / лимит (`pool_size` + `max_overflow`); на backend, llm-worker и parse-worker |
| **Loki** | Хранение логов (filesystem, retention 30 дней — `observability/loki-config.yml`) |
| **Alloy** | Собирает stdout контейнеров compose-проекта через `docker-socket-proxy` (только чтение контейнеров, сетей и логов; сам `docker.sock` в Alloy не монтируется, Alloy работает не под root), парсит `level`/`logger` (labels) и `request_id`/`trace_id` (structured metadata) из формата логов и шлёт в Loki; принимает OTLP-трассы от backend и воркеров, отбрасывает шумные span'ы `connect` SQLAlchemy и отправляет в Tempo (`observability/alloy-config.alloy`) |
| **Tempo** | Хранение трасс (local, retention 7 дней — `observability/tempo-config.yml`) |

**Затор очереди LLM:** смотреть дашборд **LLM jobs / queue** — растут `llm_rq_queue_jobs` и `llm_jobs_by_status{status="queued"}`; worker latency в `llm_worker_job_duration_seconds`. TraceQL: `{ name = "llm_job.run" }`, `{ name = "llm_job.enqueue" }`.

**Прогон парсинга:** дашборд **Parse run** — итоги за выбранный период (посты, кандидаты, LLM-вызовы, стоимость, FloodWait), время по фазам, воронка AI, живой поток постов, Telegram fetch, LLM (полный вызов vs ожидание RPM-лимита, повторы, $/мин), воркеры (heartbeat, RAM, CPU, `up`), таблица трасс `parse_run` и логи parse-worker. Трасса: `parse_run` → `parse.fetch_posts` → `telegram.channel` (канал, постов, просмотрено, секунды пауз `telegram.pause_seconds`, events `telegram.flood_wait`); `parse.process_posts` → `chat <model>` (атрибуты `llm.rate_gate.wait_seconds`, `llm.retries`, `llm.cost_usd`) и `parse.flush_vacancies`. У каждого процесса свой `service.name` (`OTEL_SERVICE_NAME`): `jobdesk-parse-worker` и т.д. TraceQL: `{ resource.service.name = "jobdesk-parse-worker" && name = "parse_run" }`.

**Пул БД:** дашборд **DB pool** — `db_pool_checked_out` / `db_pool_checked_in` / `db_pool_overflow` / `db_pool_max_connections`. Утилизация ≈ `checked_out / max_connections` (по job).

**Нагрузочный тест:** дашборд **k6 load test** — RPS, p50/p95/p99, ошибки и VU k6 (remote write, `PROM_RW=1`) рядом с RPS, задержками и пулом БД стенда `lt-api` (job `jobdesk-loadtest`). Порядок — [scripts/loadtest/README.md](scripts/loadtest/README.md).

Конфигурация: `observability/prometheus.yml`, `observability/alerts/`, `observability/alertmanager.yml`, `observability/loki-config.yml`, `observability/tempo-config.yml`, `observability/alloy-config.alloy`, provisioning Grafana — `observability/grafana/provisioning/` (datasources Prometheus, Loki и Tempo с переходами лог ↔ трасса, Alertmanager).

### Алерты

Prometheus вычисляет правила из `observability/alerts/jobdesk.yml` и отдаёт сработавшие в
Alertmanager. **Доставки наружу нет**: алерты видны в UI Alertmanager (http://localhost:9093)
и в Grafana → Alerting (правила — источник Prometheus, сработавшие и silences —
Alertmanager). Пороги — в `openspec/specs/platform/alerting`.

| Алерт | Severity | Когда |
|---|---|---|
| `JobLeaseExpired` | critical | прогон, LLM-задача или HH sync в `running` с истёкшим lease дольше 5 мин (`db_jobs_lease_expired{kind}`): recover не работает |
| `ParseQueueStuck` | critical | прогон в очереди `parse` дольше 10 мин — parse-worker его не берёт |
| `LlmQueueGrowing` | warning | очередь `llm` 15 мин не пустела и выросла (держится 5 мин) |
| `ParseRunFailed` | warning | за последние 24 ч есть прогон `failed` |
| `LlmDisabled` | warning | за последние 24 ч разбор продолжал без LLM: `circuit_breaker`, `quota`, `init_failed` |
| `FxRatesStale` | warning | последний курс ЦБ старше 3 суток дольше часа |
| `ApiOverloaded` | warning | 503 `OVERLOADED` — больше 1% запросов и больше 0,1/с 5 мин подряд |
| `TargetDown` | critical | backend или воркер не отдаёт `/metrics` 5 мин, в т.ч. остановленный контейнер |
| `WorkerMissing` | critical | у llm-, parse-, hh- или maintenance-worker нет ни одной цели 5 мин (не запускался с момента старта Prometheus) |
| `PgBackupStale` | critical | проверенный дамп старше 1,5 × `BACKUP_INTERVAL_HOURS` дольше часа |
| `PgBackupFailed` | critical | последняя попытка бэкапа провалилась (до следующей удачной) |
| `PgBackupMetricsMissing` | warning | метрик бэкапа нет 30 мин (pg-backup не пишет `pg_backup.prom` или Alloy его не читает) |

Алерты о событиях (`ParseRunFailed`, `LlmDisabled`) держатся 24 часа — без доставки короткий
алерт никто бы не увидел. Метрики бэкапа идут не скрейпом: `pg-backup` пишет
`pg_backup.prom`, Alloy читает его textfile-коллектором и отправляет в Prometheus
(`job="pg-backup"`).

- **Заглушить алерт** (например, `FxRatesStale` на новогодние каникулы, когда ЦБ не
  публикует курсы) — silence в UI Alertmanager или Grafana → Alerting → Silences.
- **Подключить доставку** (Telegram, почта) — получатель `ui-only` в
  `observability/alertmanager.yml`, пример там в комментарии. Секреты — только файлом
  (`bot_token_file` и т.п.): Alertmanager не подставляет переменные окружения.
- **Проверка правил** после правки: `bash scripts/check_alerts.sh` (Docker; `promtool
  check config`, юнит-тесты `observability/alerts/tests/`, `amtool check-config`). Тест
  `tests/test_alert_rules.py` ловит метрику в правиле, которой код больше не отдаёт.

**HTTP-лог** (`backend/http_logging.py`, логгер `backend.http`, вместо `uvicorn.access`). Каждому запросу присваивается `request_id` (UUID; валидный входящий `X-Request-ID` переиспользуется), он возвращается в заголовке ответа `X-Request-ID` и попадает в **каждую** строку лога, записанную во время запроса (и в логи роутов/сервисов): `... | backend.http | request_id=<uuid> | ...`. На запрос — одна запись после ответа:
`RESPONSE METHOD path status Nms {json}`. В JSON — `status`, `duration_ms`, `headers` и `body` ответа, а в `request` — `client`, `headers` и `body` запроса. Начало долгого запроса (SSE, экспорт) видно в трассе.

Тела пишутся до `HTTP_LOG_BODY_LIMIT` байт для JSON / form / `text/*` / XML (SSE, бинарные ответы и `Content-Disposition: attachment` — без тела). Маскируются `Authorization` (остаётся схема: `Bearer ***`), `Cookie`/`Set-Cookie`, `X-API-Key`, query-параметры и ключи тела вида `password`/`token`/`access_token`/`ticket`/`secret`/`api_key`. Уровень `RESPONSE`: 4xx — `WARNING`, 5xx — `ERROR`. Тело не длиннее лимита разбирается целиком; длиннее — пишется началом с пометкой `…[truncated, N bytes]`, секреты в начале маскируются регулярными выражениями, включая значение, обрезанное на границе. Не логируются шумные эндпоинты из `HTTP_LOG_EXCLUDE_PATHS` (по умолчанию health-check, агрегаты `/vacancies/metrics` и `/analytics/*`, Swagger/ReDoc/OpenAPI, favicon) и CORS preflight (`OPTIONS` с `Access-Control-Request-Method`).

Alloy кладёт `request_id` в **structured metadata** Loki (не label — уникален на запрос). В Grafana Explore:

```logql
# всё по одному запросу: логи обработчика и запись RESPONSE
{service="backend"} | request_id="3f2b8c1e-0d4a-4c7e-9a51-2b6f1d9e8a70"

# разобрать JSON HTTP-записей (поля status, duration_ms, body_*, headers_*, request_*)
{service="backend", logger="backend.http"} | regexp `(?P<http>\{.*\})$` | line_format "{{.http}}" | json
```

### Трассировка (OpenTelemetry → Tempo)

Трасса показывает, на что ушло время внутри одного запроса или прогона: дерево span'ов с длительностями. `backend/tracing.py` поднимает OpenTelemetry SDK при `OTEL_ENABLED=true`. Цепочка: backend → OTLP/HTTP → Alloy (batch) → Tempo → Grafana.

| Что трассируется | Как |
|---|---|
| Входящие HTTP | FastAPI-инструментация; span'ы `send`/`receive` отключены, пути из `HTTP_LOG_EXCLUDE_PATHS` не трассируются, секреты в query (`?ticket=` и т.п.) маскируются в атрибутах. Атрибут `request_id` — тот же, что в логах и `X-Request-ID` |
| SQL | SQLAlchemy-инструментация (текст запроса с плейсхолдерами, без значений параметров) |
| Исходящие HTTP | httpx-инструментация: OpenRouter (через openai SDK), ЦБ |
| LLM | `chat <model>`: `gen_ai.request.model`, `gen_ai.usage.input_tokens`/`output_tokens`, `llm.task` (`extract`/`match`/`cover_letter`), `llm.outcome`. Промпты и ответы в span не пишутся |
| Прогон парсинга | Отдельная трасса `parse_run` (со ссылкой на `POST /runs`): `parse.fetch_posts` (Telethon, фоновый поток) и параллельно `parse.process_posts` → LLM-вызовы из пула потоков (контекст пробрасывается в воркеры) |
| Матчинг / письма / курсы ЦБ | `vacancy.match`, `cover_letter.generate`, `fx.sync_on_startup` |

Sampling: доля трасс — `OTEL_TRACES_SAMPLE_RATIO`. Sampler отбрасывает SQL/HTTP-span'ы без родителя: COUNT'ы `db_*`-коллектора при scrape `/metrics` и фоновые запросы иначе дали бы тысячи трасс из одного span'а. Без `OTEL_ENABLED` (CLI, тесты) API OpenTelemetry работает как no-op.

**Связь логов и трасс.** Внутри span'а каждая строка лога получает `trace_id`: `... | request_id=<uuid> trace_id=<32 hex> | ...`. Alloy кладёт его в structured metadata. В Grafana:

- в Loki у строки с `trace_id` есть кнопка **«Открыть трассу»** (derived field);
- в Tempo у span'а есть **«Logs for this span»**: это логи с тем же `trace_id`;
- поиск в Tempo (TraceQL): `{ span.request_id = "<uuid>" }`, `{ name = "parse_run" }`, `{ span.llm.task = "match" && duration > 10s }`.

Из health-check и OpenAPI HTTP-метрики не собираются (шум от probes и документации). LLM-метрики пишутся при парсинге с `ai.enabled: true` в том же процессе backend. При недоступной БД `db_*` gauges отдают пустой набор — scrape не падает.

## Производительность и нагрузочный тест

Нагрузочный тест без LLM — `scripts/loadtest/` (k6, копия базы, стенд, HTML-отчёт,
метрики в Prometheus/Grafana), порядок работы — [scripts/loadtest/README.md](scripts/loadtest/README.md).

Что влияет на пропускную способность API:

- **`API_WORKERS`** — главный рычаг: один процесс упирается в GIL на ~1 ядре, 4 процесса
  дают ×2–2.7, 8 — ~×3.6 (на машине, где k6 и Postgres делят те же ядра).
- **`APP_ENV=prod`** (или `HTTP_LOG_BODIES=false`): тела не пишутся в HTTP-лог — +15–25%
  на списках.
- **`OTEL_TRACES_SAMPLE_RATIO=0.1`**: трассы создаются для 10% запросов — +10–20%.
- Поиск `q=` упирается в Postgres: ранжирование ограничено окном 1000 совпадений
  (см. [Поиск и пресеты фильтров](#поиск-и-пресеты-фильтров)).

Сколько выдерживает (смесь запросов UI, реальная база ~1 800 вакансий, 4 процесса, OTel
включён, k6 и Postgres на той же машине, постоянный поток запросов):

| Поток, запросов/с | Обслужено | p99 успешных | Отказы 503 |
|---|---|---|---|
| 300 | 300 | 0,10 с | 0 |
| 400 | 400 | 0,15 с | 0 |
| 450 | 444 | 0,51 с | 0 |
| 600 | ~430 успешно | 2,2 с | 24% |
| 800 | ~400 успешно | 2,2 с | 46% |

Без потерь — до ~400 запросов/с. Выше лишнее получает 503 `OVERLOADED` не позже чем
через `API_QUEUE_TIMEOUT_SECONDS`, а после спада нагрузки API сразу отвечает как обычно (см.
«Защита от перегрузки»). До неё API при 325 запросах/с зависал целиком примерно на 5 минут.

Замеры и разбор узких мест — `openspec/changes/archive/*-api-throughput/design.md` и
`*-api-overload-protection/design.md`.

### CI (GitHub Actions)

Workflow `.github/workflows/ci.yml` запускается **только вручную**: Actions → CI →
Run workflow, ветка выбирается в том же окне. Автозапусков на push / pull request нет,

## Архитектура

```text
[React UI] ──REST/SSE──► [FastAPI backend] ──enqueue──► Redis (RQ)
                              │                              │
                              ▼                              ├── parse-worker → parse_runner
                         PostgreSQL (SoT: status/progress)   │     ├── Telethon
                              ▲                              │     ├── extraction/ / ai/
                         UPSERT vacancies                    │     └── filters → dedup → metrics
                              │                              ├── llm-worker (match / cover letter / import)
                              │                              └── hh-worker → HH.ru API
```

- **`extraction/`** — быстрые эвристики (всегда).
- **`ai/`** — опционально: OpenRouter, JSON-схема, кэш, `merge_rules_and_ai`.
- **`hh/`** — sync вакансий HH.ru без LLM (admin).
- **`backend/`** — API, durable прогоны и LLM-джобы через RQ (`parse-worker` /
  `llm-worker`) или `inprocess` без Redis; прогресс прогона — колонка
  `parse_runs.progress` + SSE.
